# Stack, persistence, auth & deployment

Research lane F for the Linear clone. Everything here is aimed at one shape of
deliverable: a repository somebody clones, runs with `npm install && npm run dev`
against nothing at all, and can also deploy to a free Vercel account and use with
four colleagues signed in at once.

Confidence is marked **HIGH** (read off a primary source, quoted below),
**MED** (secondary source, consistent across several), or **LOW** (inference —
flagged as unverified).

---

## 1. Framework: Next.js 16 App Router

### Current stable

`next@16.3.0`, `react@19.2.8`, `react-dom@19.2.8` — confirmed against the npm
registry on 2026-08-13 (`npm view next version`). The five sibling projects in
this repo (`bet`, `dollar-pixels`, `fake-phone`, `Notion`, `super-smash`) all pin
exactly `next: "16.3.0"` and `react: "19.2.8"`, unpinned only for devDeps.
**Match them.** A Linear clone gains nothing from being the one project on a
different minor, and the Playwright/Vitest/Tailwind versions in this repo are
already known-good against 16.3.0. **HIGH**

App Router is the right choice and effectively the only one: Next 16 documents
`app/` as the default, and the whole caching/streaming surface described below is
App-Router-only. There is no argument for `pages/` here.

### What Next 16 changes that this build will actually hit

Source for all of the following: <https://nextjs.org/docs/app/guides/upgrading/version-16>
(fetched 2026-08-13, doc version 16.3.0). **HIGH**

**Async request APIs — no longer a compatibility period, fully removed.**
`cookies()`, `headers()`, `draftMode()`, and `params`/`searchParams` are
promises. Every dynamic route in a Linear clone is `/[workspace]/issue/[id]`
shaped, so this is not an edge case:

```tsx
// app/[workspace]/issue/[key]/page.tsx
export default async function Page(props: PageProps<'/[workspace]/issue/[key]'>) {
  const { workspace, key } = await props.params
  const query = await props.searchParams
  // ...
}
```

`PageProps` / `LayoutProps` / `RouteContext` are globally available type helpers
generated by `npx next typegen`. Use them rather than hand-writing
`{ params: Promise<{ key: string }> }` — they stay in sync with the route tree.

**`middleware.ts` is renamed to `proxy.ts`.** The named export becomes `proxy`,
and config flags rename with it (`skipMiddlewareUrlNormalize` →
`skipProxyUrlNormalize`). Critically: **`proxy` runs on the Node runtime only and
that is not configurable.** If you want the Edge runtime you must keep the
deprecated `middleware` filename. For this build, Node `proxy.ts` is what we
want anyway — session lookup wants Node crypto.

> A caution from the sibling `bet`: pinning `turbopack.root` in `next.config.ts`
> matters in this repo, because Turbopack walks up looking for the highest
> lockfile and can land on a sibling project. `bet` lost `proxy.ts` silently
> because of it. Copy the `turbopack.root` pin from `dollar-pixels/next.config.ts`.

**Turbopack is the default for `next dev` and `next build`.** Drop `--turbopack`
from scripts. A custom `webpack` config now *fails* the build unless you pass
`--webpack`. We have no webpack config, so this is free — but it constrains one
option below: anything that needs a webpack loader (some WASM setups) is a cost.

**Caching APIs changed shape.** This is the part that bites a collaborative app:

- `revalidateTag(tag)` now requires a second argument, a `cacheLife` profile:
  `revalidateTag('issues', 'max')`. The one-argument form is a TypeScript error.
- **`updateTag(tag)`** is new and is a Server-Actions-only API with
  *read-your-writes* semantics — it expires and immediately refreshes within the
  same request. This is exactly what an issue-status change needs: the person who
  dragged the card must see it land, not stale data.
- **`refresh()`** (from `next/cache`) refreshes the client router from a Server
  Action. This is the cheap "something changed, re-pull" primitive we lean on for
  the realtime fallback in §6.
- `cacheLife` and `cacheTag` are stable — drop the `unstable_` aliases.

**`use cache` / `dynamicIO` / PPR are all now one flag: `cacheComponents: true`.**
`experimental.dynamicIO` and `experimental.useCache` are removed;
`experimental_ppr` as a segment config is removed. **Recommendation: leave
`cacheComponents` off.** Next's own guide is explicit that turning it on "is not
a rename-only change: it can surface build errors for uncached data outside of
`<Suspense>` and requires adopting the Cache Components model." A Linear clone is
almost entirely per-user, per-workspace dynamic data behind auth; the caching
model buys us little and costs a migration. **HIGH**

**React 19.2 features that are worth using here:**
- `useOptimistic` — the single most valuable React feature for this clone.
  Linear's defining feel is that state changes land instantly. Wrap issue
  mutations in `useOptimistic` + a Server Action so the board reorders before the
  round-trip.
- `useEffectEvent` — for the SSE subscription effect, so the handler can read the
  latest state without re-subscribing on every render.
- `<ViewTransition>` — animate list→detail navigation. Optional polish.
- `<Activity>` — keep a hidden panel's state alive.

**React Compiler is stable but off by default** (`reactCompiler: true`, needs
`babel-plugin-react-compiler`). It routes builds through Babel and slows them.
**Leave it off** for now; it is a late optimisation, not a stack decision.

### Gotchas specifically relevant to this build

- **Parallel routes now require an explicit `default.js` per slot** or the build
  fails. A Linear clone wants an intercepted-route modal for issue detail
  (`@modal`), so this will come up. `export default function Default() { return null }`.
- **Server Actions and `useOptimistic`**: an action that throws leaves the
  optimistic state applied until the transition settles. Plan for a revert path.
- `next lint` is gone; `next build` no longer lints. The siblings already run
  `eslint .` as a separate script — keep that.
- `serverRuntimeConfig`/`publicRuntimeConfig` are removed; env vars only. To read
  an env var at *runtime* rather than build time, `await connection()` first.
- Node 20.9+ and TypeScript 5.1+ minimums. We have Node 26 / TS 5.x. Fine.

**Decision: Next.js 16.3.0 + React 19.2.8 on the App Router, pinned exactly as the sibling projects pin them, with `cacheComponents` and `reactCompiler` left off** — because the sibling versions are already proven against this repo's Playwright/Vitest/Tailwind stack, and Cache Components is a migration with no payoff for an app whose every page is per-user dynamic data.

## 2. Database on a free tier

### First, the thing that changed

**Vercel Postgres no longer exists.** Vercel's own docs
(<https://vercel.com/docs/postgres>, last updated 2026-01-13) state that existing
Vercel Postgres databases were automatically moved to Neon in December 2024.
Postgres on Vercel is now Marketplace-only. `@vercel/postgres` still resolves on
npm but is a legacy shim; new code targets the provider. **HIGH**

### The candidates

| | Free tier | Idle behaviour | Connection model | Vercel Edge / Node |
|---|---|---|---|---|
| **Neon** | 0.5 GB storage, **100 CU-hours/project/month**, 5 GB egress, 100 projects, 10 branches | **Scale-to-zero after 5 min, always on, cannot be disabled.** Resume is sub-second. Over-limit **suspends compute until next month; data is kept** | `neon()` = SQL over HTTP (fetch); `Pool`/`Client` = WebSocket, drop-in for `pg`. PgBouncer pooled endpoint built in | **Both** |
| **Supabase** | 500 MB DB, 5 GB egress, 50k MAU, **2 projects** | **Projects pause after ~7 days of low activity**; data restorable up to 1 year | Supavisor transaction mode :6543 (IPv4, needs `prepare: false`); direct :5432 is **IPv6-only** without the paid add-on | Node yes, edge via pooler |
| **Turso / libSQL** | 100 DBs, 5 GB, 500M row-reads/mo | none | `@libsql/client` over HTTP/WS | Both |
| **Cloudflare D1** | 5M row-reads/day, 100k writes/day, 5 GB | none | Workers **bindings**; REST API exists but Cloudflare says it is "best suited for administrative use" and it shares the global API rate limit | **Not reachable from Vercel** without deploying a proxy Worker |
| **PlanetScale** | **none** — Hobby killed 2024-03-06, nothing reversed it | — | — | — |
| **Prisma Postgres** | 500 MB, **100,000 operations/month**, 50 DBs | markets "zero cold starts" | direct TCP went GA 2025 (`db.prisma.io:5432`), so usable **without** Prisma ORM | Node |

Also checked: **Xata** (free tier gone; 14-day trial then pay-as-you-go),
**Nile** (~1 GB free, vendor-unverified), **Aiven** (genuine free forever but
1 GB, **no connection pooler**, and an explicit "unused for an extended period"
shutdown clause), **Railway** (no free tier), **Render** (free Postgres
**deleted 44 days after creation** — 30-day life plus 14-day grace).

### The two that eliminate themselves on the requirement

The brief's operating scenario is a reviewer who clones this, deploys it, and
comes back to it later.

- **Supabase pauses after ~7 days of low activity.** The reviewer returns to a
  dead app. Fatal, and it is documented vendor behaviour, not an edge case.
- **Render deletes the database and all its data at day 44.** Fatal.

Turso works but is the wrong dialect (SQLite), which per §3/§4 costs a whole
second schema — and the engine is mid-rewrite, with the Rust "Turso Database"
still in beta and a Postgres frontend announced in July 2026 as experimental.
D1 cannot be reached from Vercel without a second deployment. PlanetScale has no
free tier. Prisma Postgres is the genuine runner-up — zero cold start, direct TCP
now GA — but **100,000 operations/month** is the binding constraint for a
multi-user app that polls for changes (§6), and it has no equal-smoothness
Vercel provisioning flow.

### Why Neon

The decisive property is not the storage number, it is that **Neon is a
first-party Vercel Marketplace integration**: installing it from the Vercel
dashboard provisions the database and injects the connection strings into the
project's environment with no copy-paste step. Vercel Hobby maps to the Neon Free
plan. Idle costs a sub-second cold start, not a paused project. Going over a
monthly limit suspends compute until the next month; **it does not delete data**.

**Caveat, stated plainly.** The "won't be deleted after a week of not using it"
property is strongly implied by Neon's documented behaviour — scale-to-zero is
not pausing, storage persists, over-limit suspends compute only — but I could
find **no explicit vendor promise** never to reap idle free projects, and no
statement that they do. **MED, one step short of verified.**

Also worth knowing: Neon's own docs describe resume as "a few hundred
milliseconds", but third-party measurements scatter from 100 ms to 800 ms and I
found **no authoritative published cold-start figure**. Budget 0.3–1 s for the
first query after idle, and note that this lands on the *first request after five
idle minutes* — i.e. exactly the reviewer's first page load. Consider a trivial
warmup query from the landing page.

### Exact connection setup

```bash
npm i drizzle-orm @neondatabase/serverless
npm i -D drizzle-kit
```

**Two URLs, and the split is load-bearing.** These are the exact names the
Vercel Marketplace integration injects, so a Marketplace install needs no manual
step:

```bash
# App runtime — POOLED. Note "-pooler" in the hostname.
DATABASE_URL="postgresql://USER:PASSWORD@ep-xxx-pooler.REGION.aws.neon.tech/DBNAME?sslmode=require&channel_binding=require"

# Migrations, seeds, pg_dump — DIRECT. Same string with "-pooler" removed.
DATABASE_URL_UNPOOLED="postgresql://USER:PASSWORD@ep-xxx.REGION.aws.neon.tech/DBNAME?sslmode=require&channel_binding=require"
```

Neon explicitly warns that running migrations over the **pooled** string causes
errors: PgBouncer transaction mode breaks DDL tooling, `SET`-based session state,
SQL-level `PREPARE`/`DEALLOCATE`, `LISTEN`/`NOTIFY`, and `pg_dump`/`pg_restore`.
Driver-level (protocol) prepared statements on the pooled endpoint are fine. The
pooled endpoint takes up to 10,000 client connections — which is what makes it
safe for serverless functions that each open their own.

`sslmode=require` is mandatory. `channel_binding=require` is Neon's documented
default but is honoured by libpq-based drivers and **ignored by most others**; if
a tool rejects it, drop the parameter.

Runtime client:

```ts
// src/adapters/db/neon.ts
import 'server-only'
import { neon } from '@neondatabase/serverless'
import { drizzle } from 'drizzle-orm/neon-http'
import * as schema from './schema'

const sql = neon(process.env.DATABASE_URL!)      // POOLED
export const db = drizzle(sql, { schema })
```

`neon()` is SQL-over-HTTP: one statement per round trip, plus a `transaction()`
batch helper. It works on both the Vercel Edge and Node runtimes. **If you need
interactive multi-statement transactions** — and an issue-reorder that renumbers
siblings probably does — swap to `drizzle-orm/neon-serverless` with the WebSocket
`Pool`, which is a drop-in for `pg`. On Node 22+ the built-in `WebSocket` is used;
below that you must set `neonConfig.webSocketConstructor = ws`. We are on Node 26,
so no `ws` dependency.

**Decision: Neon Free, provisioned through the Vercel Marketplace, with `DATABASE_URL` (pooled) for the app and `DATABASE_URL_UNPOOLED` (direct) for migrations, accessed via `@neondatabase/serverless` + `drizzle-orm/neon-http`** — because it is the only free Postgres that neither pauses after a week of inactivity (Supabase) nor deletes the data outright (Render), and the Marketplace integration means the reviewer never copies a connection string by hand.

## 3. ORM: Drizzle

### The comparison, and the one fact that settles it

|  | Drizzle `0.45.2` | Prisma `7.x` |
|---|---|---|
| Bundle | ~7.4 kB, no engine | ~1.6 MB gzipped since the Rust engine was replaced by a TS/WASM query compiler in Prisma 7 (Nov 2025) — down from ~14 MB |
| Cold start | no engine to load; ~10–50 ms connection setup | ~40–80 ms engine load, ~80–150 ms to first query |
| Migrations | `drizzle-kit generate` → SQL files in `drizzle/`, `drizzle-kit migrate` applies them; `drizzle-kit push` for throwaway dev | `prisma migrate dev` / `deploy`, own migration engine |
| Schema | TypeScript, dialect-specific (`pgTable`) | `schema.prisma` DSL, separate codegen step |
| Type safety | inferred straight from the schema objects, no codegen | generated client, needs `prisma generate` in the build |

Sources: [Bytebase](https://www.bytebase.com/blog/drizzle-vs-prisma/), [makerkit](https://makerkit.dev/blog/tutorials/drizzle-vs-prisma), [Drizzle Kit docs](https://orm.drizzle.team/docs/kit-overview). **MED** on the benchmark numbers (secondary sources, consistent with each other), **HIGH** on the migration commands and schema mechanics (vendor docs).

Prisma 7 closed most of the gap that used to make this a walkover — the 14 MB
Rust binary is gone. It is now a defensible choice. Two things still decide it
for this build:

1. **No codegen step.** Prisma needs `prisma generate` to run before typecheck,
   which means a `postinstall` hook and a build-order constraint. Drizzle's types
   come from the schema objects themselves. For a repo whose headline claim is
   "clone it and `npm run dev`", one fewer generated artifact matters.
2. **Drizzle's PGlite support is first-party and uses the same `postgresql`
   dialect as production** (§4). This is the fact that settles it, and it is worth
   being precise about, because it cuts both ways — see the warning below.

### The trap: Drizzle schemas are dialect-specific

`pgTable` and `sqliteTable` are different builders producing different types.
There is **no** one-schema-two-dialects mode. If the local database is SQLite and
the deployed one is Postgres, you maintain **two schema files and two migration
histories** for the same domain — which for a Linear clone (workspaces, teams,
memberships, projects, issues, states, labels, comments, cycles, activity) is a
large and permanently drifting surface.

This is the single strongest argument for the PGlite answer in §4: it keeps
`dialect: 'postgresql'` for both, so there is exactly one `schema.ts` and exactly
one `drizzle/` folder. **HIGH** (confirmed against
<https://orm.drizzle.team/docs/connect-pglite>, which sets `dialect: 'postgresql'`
for PGlite projects).

### Testing story

Drizzle runs against a PGlite instance created per test file with
`new PGlite()` (no `dataDir` — pure in-memory), so unit tests exercise **real
Postgres semantics** rather than a SQLite approximation: real `ON CONFLICT`, real
`SELECT … FOR UPDATE`, real transactional DDL, real `citext`/`jsonb` if we use
them. That is strictly better than the usual "SQLite in tests, Postgres in prod"
arrangement, where the test suite cannot catch a Postgres-only bug.

### Workflow

```jsonc
// package.json scripts
{
  "db:generate": "drizzle-kit generate",       // schema.ts -> drizzle/NNNN_*.sql
  "db:migrate":  "tsx scripts/migrate.ts",     // applies to whichever driver is configured
  "db:studio":   "drizzle-kit studio",
  "db:seed":     "tsx scripts/seed.ts"
}
```

```ts
// drizzle.config.ts
import { defineConfig } from 'drizzle-kit'

export default defineConfig({
  dialect: 'postgresql',
  schema: './src/adapters/db/schema.ts',
  out: './drizzle',
  // Only used by `drizzle-kit push` / `studio` against a real Neon database.
  // The DIRECT (unpooled) URL — PgBouncer transaction mode breaks DDL tooling.
  dbCredentials: { url: process.env.DATABASE_URL_UNPOOLED ?? process.env.DATABASE_URL! },
})
```

Day-to-day loop:

```bash
# 1. edit src/adapters/db/schema.ts
npm run db:generate          # writes drizzle/0007_add_issue_cycle.sql + snapshot
npm run db:migrate           # applies pending files to the local PGlite dir
git add drizzle/ src/adapters/db/schema.ts
```

Never `drizzle-kit push` against Neon. `push` diffs and applies immediately with
no migration history and can silently drop a column when the schema removes one.
`generate` + `migrate` is the reviewable path, and it is also the only path that
works for the deploy story in §8, where migrations run from CI rather than a
shell on the server.

**Decision: Drizzle ORM `^0.45` with `drizzle-kit ^0.31`, one `postgresql`-dialect schema and one migration folder shared by PGlite locally and Neon in production** — because it has no codegen step, and because keeping a single dialect is what makes the zero-config local story in §4 possible without maintaining the whole schema twice.

## 4. Zero-config local run

### The requirement, restated precisely

`git clone && npm install && npm run dev` must produce a working, multi-user-
demoable app with **no `DATABASE_URL`, no Docker, no `createdb`, no account
signup** — while the deployed build uses real Postgres, and while the SQL that
runs locally is the *same SQL* that runs in production. The last clause is the
one that eliminates most of the options.

### (a) Repository port + in-memory adapter

Write a `Store` interface, implement it twice: a `Map`-backed adapter for local,
a SQL adapter for Neon.

This is what the sibling `dollar-pixels` does, and its research notes are worth
inheriting wholesale (`dollar-pixels/research/persistence-and-vercel.md` §4):

> A naive `const rows = new Map()` at module scope breaks twice: Next's Fast
> Refresh re-evaluates modules on file change, re-running top-level code and
> wiping the map; and multiple workers in dev — and multiple function instances
> in production — each get their own copy.
>
> …in Next 16 a Server Component's module graph and a Route Handler's module
> graph are bundled as separate layers, so even a plain module-level singleton is
> constructed *twice*.

The fix, already proven in two sibling projects, is to key the instance off
`Symbol.for()` on `globalThis`:

```ts
const REGISTRY: unique symbol = Symbol.for('linear.store.v1')
export function storeRegistry(): StoreRegistry {
  const g = globalThis as typeof globalThis & { [REGISTRY]?: StoreRegistry }
  return (g[REGISTRY] ??= {})
}
```

**Why it still loses here.** For `dollar-pixels` the domain was small enough that
writing every query twice was affordable. A Linear clone is not: workspaces,
teams, memberships with roles, invites, projects, issues, sub-issues, states,
priorities, labels, comments, cycles, activity feed, saved views. Two hand-written
implementations of that means the deployed SQL path is only ever exercised in
production, which is exactly where you cannot afford to find out it is wrong.

### (b) PGlite — embedded Postgres in WASM

[PGlite](https://pglite.dev) is a real Postgres compiled to WASM, ~2.6 MB gzipped,
shipped as `@electric-sql/pglite` (`0.5.5`). Not a VM, not an emulation layer —
Postgres itself. It runs in Node with either no persistence at all (in-memory) or
a `dataDir` on the filesystem. Drizzle supports it first-party via
`drizzle-orm/pglite` and `drizzle-orm/pglite/migrator`, at `dialect: 'postgresql'`. **HIGH**

That gives the property nothing else gives: **the same schema, the same migration
files, the same queries, the same SQL dialect, locally and in production.** One
adapter, not two. The local database is not a simulation of the deployed one; it
is the same database engine.

**The constraint you must design around: PGlite is single-connection, and two
processes on one `dataDir` will corrupt it.** PGlite is single-user/single-
connection by design (WASM is single-process); field reports document concurrent
processes sharing a `dataDir`, both holding read-write descriptors on the same WAL
segment, producing WAL/checkpoint corruption that needed a full reimport. **MED**
(vendor docs are explicit about single-connection; the corruption report is a
third-party issue tracker).

Consequences, and how we handle each:

| Situation | Handling |
|---|---|
| RSC layer and Route Handler layer both open the store | `globalThis` `Symbol.for` singleton — the same fix as (a). One PGlite instance per process. |
| Vitest workers run in parallel | Each test file constructs `new PGlite()` with **no `dataDir`** — pure in-memory, isolated, nothing on disk to contend for. Fast, and it is real Postgres. |
| Playwright + `next dev` | `webServer` with `reuseExistingServer` — one dev server, one process, one instance. Same as the sibling `playwright.config.ts`. |
| Someone runs `npm run dev` twice | **This is the real hazard.** Document it in the README, keep the `dataDir` project-local (`.data/pglite`), and gitignore it. Deleting `.data/` is always a safe recovery. |
| Deployed to Vercel | PGlite must never be selected there. See the fail-fast guard below. |

**Bundling.** PGlite ships WASM and must not be traced/bundled by Turbopack.
Add it to `serverExternalPackages` in `next.config.ts`, and import it through a
dynamic import so selecting the Neon driver never loads it:

```ts
// next.config.ts
const nextConfig: NextConfig = {
  serverExternalPackages: ['@electric-sql/pglite'],
  turbopack: { root: fileURLToPath(new URL('.', import.meta.url)) },
}
```

**MED** — the `serverExternalPackages` requirement is reported consistently by
secondary sources rather than stated in a Next.js doc page I could quote; verify
on first build. If Turbopack does trace it, the fallback is the same variable-
specifier dynamic import the sibling uses for `node:sqlite`.

### (c) SQLite via `node:sqlite` or `better-sqlite3`

`node:sqlite` is genuinely attractive and is **already proven in this repo** —
`dollar-pixels` uses it as its default local driver with no dependency at all. I
verified it is present and working on the installed runtime:

```
$ node -e "…require('node:sqlite')…"
[ 'DatabaseSync', 'StatementSync', 'Session', 'constants', 'backup' ]
[ [Object: null prototype] { a: 1 } ]
```
(Node v26.0.0.) It is multi-process safe, synchronous, zero-install, and
persists across restarts.

`better-sqlite3` is strictly worse for this: a native module that must compile
against the local ABI on `npm install` — a genuine failure mode for "clone and
run" — and unusable on Vercel regardless.

**Why SQLite still loses.** It is a *different dialect*, so per §3 it costs a
second Drizzle schema and a second migration history for the whole Linear domain.
And every Postgres-only construct the app wants — `jsonb` for issue description
docs, partial unique indexes for "one active cycle per team", `FOR UPDATE` for
ordering contention, `generated always as identity` — either has no SQLite
equivalent or has one that behaves differently. The bug you find in production is
precisely the one your local database could not express.

### Vercel's filesystem, which rules out (b) and (c) *for production*

The deployed filesystem is read-only apart from `/tmp`, and `/tmp` is per-instance
and ephemeral. A file-backed database on Vercel means every function instance has
its own private copy of the data, which for a multi-user collaborative app is not
a degraded mode — it is silent, undetectable data loss. Two people editing the
same issue would each be talking to a different database and neither would see an
error.

**So the adapter selection must fail loudly, not fall back quietly.**

### The recommended selection logic

```ts
// src/adapters/db/index.ts
import 'server-only'

export type DbDriver = 'pglite' | 'neon'

export function dbDriver(): DbDriver {
  const explicit = (process.env.DB_DRIVER ?? '').trim().toLowerCase()
  if (explicit === 'pglite' || explicit === 'neon') return explicit
  if (explicit !== '') {
    throw new Error(`Unknown DB_DRIVER "${process.env.DB_DRIVER}". Expected "pglite" or "neon".`)
  }

  const hasUrl = Boolean(process.env.DATABASE_URL?.trim())
  if (hasUrl) return 'neon'

  // The guard that matters. A deployed build with no DATABASE_URL would run on
  // a per-instance ephemeral database: two users, two databases, no error.
  // Refuse to boot instead.
  if (process.env.VERCEL === '1' || process.env.NODE_ENV === 'production') {
    throw new Error(
      'No DATABASE_URL. PGlite is a local-development driver: on Vercel the ' +
      'filesystem is per-instance and ephemeral, so each function instance ' +
      'would get its own private copy of the data. Provision Postgres (Neon) ' +
      'and set DATABASE_URL.',
    )
  }
  return 'pglite'
}
```

Two rules encoded here, both learned from the sibling's post-mortems: an
**unrecognised** value is an error rather than a silent fallback (`STORE_DRIVER=Postgres`
booted `dollar-pixels` on the wrong adapter and it served traffic while forgetting
every purchase), and the **dangerous default is refused in the dangerous place**.

The instance itself, memoised on `globalThis` and loaded lazily so choosing one
driver never pulls in the other:

```ts
const REGISTRY: unique symbol = Symbol.for('linear.db.v1')

export async function getDb(): Promise<Db> {
  const g = globalThis as typeof globalThis & { [REGISTRY]?: { db?: Db } }
  const reg = (g[REGISTRY] ??= {})
  if (reg.db) return reg.db

  if (dbDriver() === 'neon') {
    const { neon } = await import('@neondatabase/serverless')
    const { drizzle } = await import('drizzle-orm/neon-http')
    reg.db = drizzle(neon(process.env.DATABASE_URL!), { schema })
  } else {
    const { PGlite } = await import('@electric-sql/pglite')
    const { drizzle } = await import('drizzle-orm/pglite')
    const { migrate } = await import('drizzle-orm/pglite/migrator')
    const client = new PGlite(process.env.PGLITE_DATA_DIR ?? '.data/pglite')
    const db = drizzle({ client, schema })
    await migrate(db, { migrationsFolder: './drizzle' })   // local only — see §8
    await seedIfEmpty(db)
    reg.db = db
  }
  return reg.db
}
```

Note that migration-on-boot happens **only on the PGlite branch**. On Neon it
would run once per cold start from however many instances happen to be warming —
the same reasoning the sibling's Postgres adapter records for never issuing DDL.
Production migrations run from CI (§8).

### Seeding is not optional here

A reviewer who clones this needs to *see* multi-user collaboration, and they
cannot invite a colleague to a database that has no workspace in it. `seedIfEmpty`
should create a demo workspace, two teams, ~4 users with known passwords printed
to the console on first boot, and a few dozen issues across states — so the very
first `npm run dev` opens onto a board that looks like Linear, and a second
browser profile can sign in as a different user immediately.

**Decision: a single Drizzle `postgresql` schema behind a `getDb()` factory that selects PGlite (file-backed under `.data/pglite`, auto-migrated and auto-seeded on first boot) when `DATABASE_URL` is absent, and Neon when it is present — with a hard boot failure if `DATABASE_URL` is missing on Vercel** — because PGlite is the only option that runs the production SQL dialect locally, so there is one schema, one migration history, and no untested second query implementation.

### Why Better Auth wins on this specific app

The requirement list is: email+password signup with **no email provider** (so no
verification mail, no magic links), sessions, invite-link acceptance, workspace
membership, teams, member/admin roles. Better Auth's `organization` plugin covers
most of that shape directly — organizations, members, invitations, and
`owner`/`admin`/`member` roles, with invitations expiring after a configurable
window (default 48 h). ([plugin docs](https://better-auth.com/docs/plugins/organization)) **MED**

The no-email constraint is not a problem, it is a *fit*: the invitation flow's
`sendInvitationEmail` hook is just a function. Instead of sending mail, return the
link and render it in the UI for the inviter to copy — which is exactly the
"invite-link acceptance" the brief asks for.

```ts
organization({
  async sendInvitationEmail({ invitation, organization }) {
    // No mail provider by design. The link is surfaced in the UI instead;
    // this hook only records it so the invite dialog can show it.
    console.info(`[invite] ${organization.name}: ${appUrl}/accept-invite/${invitation.id}`)
  },
})
```

**Draw the boundary explicitly.** Let Better Auth own `user`, `account`,
`session`, `verification`, plus `organization` / `member` / `invitation` (a Linear
*workspace* is a Better Auth *organization*). Own **teams and team membership in
our own tables**, because Linear's model has two nesting levels with per-team
roles, and depending on the plugin's team-role granularity to match is a risk not
worth taking. Domain tables (project, issue, comment, cycle, label) are entirely
ours and reference `user.id`.

### Why it fits the §4 persistence design

Better Auth's `drizzleAdapter` talks to our Drizzle instance. Because PGlite and
Neon are both `postgresql`-dialect behind the same Drizzle object, auth works
identically local and deployed, with no second code path.

**Do not use Better Auth's memory adapter**, even for local dev. It has a known
Next.js App Router failure ([issue #6372](https://github.com/better-auth/better-auth/issues/6372)):
Server Components and Route Handlers are bundled as separate layers, so the same
module is evaluated twice with separate memory spaces and a signed-in user in an
RSC is "Account not found" in a Route Handler. This is the same module-duplication
trap documented in §4 — and it is a further argument for PGlite, which sidesteps
it because the store is a file, not a `Map`. **MED**

One documented caveat to design around: *"As RSCs cannot set cookies, the cookie
cache will not be refreshed until the server is interacted with from the client

cache for authorization decisions that must be instantly revocable. Membership
and role checks should hit the database.

### Session and cookie strategy

**Database sessions, not a self-contained JWT.** This is a deliberate choice for
a collaborative app: removing a member from a workspace, or an admin revoking
access, must take effect on the next request. A stateless JWT stays valid until
it expires, so a removed member keeps their access for up to the token lifetime —
a real correctness bug in an app whose whole point is shared, permissioned data.
Better Auth's `cookieCache` gives back most of the per-request database round-trip
without giving up revocability, because it is a short-lived (5 min) signed cache
in front of a real session row.

| Attribute | Value | Why |
|---|---|---|
| `httpOnly` | `true` | Session id must be unreachable from JS; the whole point of an opaque cookie. |
| `sameSite` | `lax` | **Not `strict`.** An invite link arrives from Slack/email and lands as a cross-site top-level GET; `strict` would drop the cookie and show the invitee a logged-out page. `lax` sends it on top-level navigations while still blocking cross-site POST/CSRF. |
| `secure` | `true` in production, `false` locally | `Secure` on `http://localhost` means the browser drops the cookie and nobody can log in on a fresh clone. |
| `path` | `/` | |
| Expiry | 7 days absolute | Long enough that a reviewer isn't re-logging-in mid-demo, short enough to bound a leaked cookie. |
| Rotation | `updateAge` 1 day | Sliding renewal: an active session's expiry is pushed out at most once a day, so the token rotates without a write on every request. |
| On privilege change | Delete the session row | Revocation is a `DELETE`, which is only possible *because* sessions are in the database. |

### Password hashing

Better Auth's default is **scrypt via `node:crypto`**, chosen because it is
natively supported by Node and needs no native module. ([security docs](https://better-auth.com/docs/reference/security)) **MED**

**Keep the default.** The alternative worth considering is Argon2id, which OWASP
lists first (`m=19456, t=2, p=1`), with scrypt second — but every Node Argon2
binding (`argon2`, `@node-rs/argon2`) is a **native module compiled at install
time**. That is a direct violation of the "clone it and `npm install` just works"
requirement, and a plausible failure on a reviewer's machine. Scrypt is on the
same OWASP recommendation list, ships with the runtime, and runs fine in the
Vercel Node runtime.

Two things to check before shipping, which I could **not** verify from the docs:

- **The exact scrypt parameters Better Auth uses (N, r, p, dkLen) are not stated
  on the security page I read.** Read `packages/better-auth/src/crypto/password.ts`
  in the installed version. If `N` is below `2^16`, override it. OWASP's 2026
  floor is `N = 2^17, r = 8, p = 1` for interactive use; `N = 2^14` is the
  minimum anyone still calls acceptable. **LOW — unverified, verify before shipping.**
- Overriding is a supported one-liner if needed:
  ```ts
  emailAndPassword: {
    password: {
      hash: async (password) => myScrypt(password, { N: 2 ** 17, r: 8, p: 1 }),
      verify: async ({ password, hash }) => myScryptVerify(password, hash),
    },
  }
  ```
  Note the migration hazard: changing the algorithm invalidates every existing
  hash. Decide before the first user exists.

**Do not use Web Crypto PBKDF2** as a substitute. It is available everywhere
including Edge, but it is not memory-hard and OWASP places it last, reserved for
FIPS compliance. We are on the Node runtime (`proxy.ts` is Node-only in Next 16
anyway), so there is no reason to reach for it.

**Decision: Better Auth `^1.6` with the Drizzle adapter, the `organization` plugin for workspaces/invitations, database-backed sessions (7-day expiry, 1-day sliding renewal, 5-minute signed cookie cache) in an `httpOnly` / `sameSite=lax` / production-only-`secure` cookie, and the default `node:crypto` scrypt hash with parameters verified against the OWASP floor** — because Auth.js is in maintenance mode, Clerk requires a third-party account before the app will run at all, and database sessions are the only strategy under which removing a workspace member actually removes their access.

### What Vercel Hobby actually allows (2026 numbers, not 2023 folklore)

times out at 10 s — that predates Fluid compute and is wrong.

### The constraint nobody mentions, which decides the design

**Provisioned memory bills for the entire instance lifetime, including idle I/O
wait.** Only *Active CPU* pauses. Hobby functions are fixed at 2 GB, so:

```
360 GB-hours ÷ 2 GB = 180 instance-hours per month ≈ 5.9 hours per day
```

That is wall-clock time during which *any* long-lived connection is open (Fluid
concurrency means many users share one instance, so it is not per-user). The
conclusion is blunt: **you cannot run a 24/7 always-connected realtime app on
Vercel Hobby.** A single dashboard tab left open around the clock is 720
instance-hours and blows the monthly budget four times over — and the penalty for
blowing it is a 503 for up to 30 days.

⚠️ Vercel does not publish the per-instance Fluid concurrency number, so I cannot
convert 180 instance-hours into a user count. **LOW** on any such conversion.

Everything below is shaped by that number.

### Why not WebSockets, even though they now work

Vercel shipped native WebSocket support in June 2026 and Hobby is not excluded.
It is still the wrong choice here:

- **Every socket dies at 300 s** on Hobby, so reconnection logic is the steady
  state rather than an edge case — you write the reconnect machinery anyway.
- **Next.js has no upgrade API.** The route is
  `experimental_upgradeWebSocket()` from `@vercel/functions`, documented as
  experimental, subject to change, and Vercel-only. First-class support exists in
  Nitro, Bun, Express, Hono — not Next.
- **In-memory rooms and presence do not work.** New connections are not
  guaranteed to reach the same instance, and after a deploy old connections stay
  on the old deployment. Vercel's own words: *"Store durable state, presence,
  counters, rooms, and pub/sub coordination in an external data store."* So you
  need Redis anyway — a second provisioning step.
- **The traffic is asymmetric.** A Linear clone is overwhelmingly server→client:
  somebody else moved a ticket. Writes are ordinary POSTs / Server Actions.
  Vercel's guidance matches: *"If the client must send data at the same rate it
  receives, choose WebSocket; otherwise, SSE paired with HTTP usually fits."*

### Why not a third-party realtime service

All of these have usable free tiers — Ably (200 peak connections, 6M msgs/mo,
the best raw headroom), Pusher Sandbox (100 concurrent, 200k msgs/day),
Redis Cloud via the Vercel Marketplace (30 connections, installs without leaving
Vercel), Upstash Redis (500k commands/mo, pub/sub works over REST, SSE
`/subscribe`), Cloudflare Durable Objects (now on the Workers **free** plan with
the SQLite backend, hibernation included), Convex, Liveblocks (10 per room — the
tightest ceiling here), Supabase Realtime (but the project pauses after a week).

Every one of them adds **a second account, a second dashboard, and a second set
of keys** to a project whose stated requirement is that a reviewer can clone it
and run it. Redis Cloud is the least bad because it installs from inside Vercel,
and it is the right escape hatch if the app outgrows the primary design — but it
should not be on the critical path for the first run.

PartyKit specifically: **do not build on it.** Cloudflare acquired it in April
2024, docs are frozen at March 2025, the hosted free tier wipes storage every 24
hours, and there is no deprecation notice *and no affirmation either*.

### Recommended primary: SSE with the database as the bus

Each client opens `GET /api/stream?since=<cursor>` — a Node-runtime Route
Handler that returns immediately and then pushes deltas:

```ts
// app/api/stream/route.ts
export const runtime = 'nodejs'
export const dynamic = 'force-dynamic'
export const maxDuration = 300

export async function GET(request: Request) {
  const session = await auth.api.getSession({ headers: request.headers })
  if (!session) return new Response('Unauthorized', { status: 401 })

  const url = new URL(request.url)
  let cursor = url.searchParams.get('since') ?? request.headers.get('last-event-id') ?? '0'

  const encoder = new TextEncoder()
  const stream = new ReadableStream({
    async start(controller) {
      const send = (s: string) => controller.enqueue(encoder.encode(s))
      const startedAt = Date.now()

      const tick = setInterval(async () => {
        // Self-close before the platform kills us, so EventSource reconnects
        // cleanly with Last-Event-ID rather than seeing a truncated stream.
        if (Date.now() - startedAt > 280_000) {
          clearInterval(tick); controller.close(); return
        }

        const events = await changesSince(session.workspaceId, cursor)   // indexed range scan
        for (const e of events) {
          cursor = e.seq
          send(`id: ${e.seq}\nevent: change\ndata: ${JSON.stringify(e)}\n\n`)
        }
        // Vercel documents that HTTP/1.1 intermediaries may close idle
        // connections and that you should "stream progress or heartbeat data".
        if (events.length === 0) send(`: ping\n\n`)
      }, 2000)

      request.signal.addEventListener('abort', () => { clearInterval(tick); controller.close() })
    },
  })

  return new Response(stream, {
    headers: {
      'Content-Type': 'text/event-stream',
      'Cache-Control': 'no-store, no-transform',
      'Connection': 'keep-alive',
      'X-Accel-Buffering': 'no',
    },
  })
}
```

Four things in there are load-bearing:

1. **Return the `Response` before awaiting the producer.** If you `await` the
   loop inside the handler, Next buffers the entire stream and nothing arrives
   until it finishes. (App-Router-specific;
   [next.js#48427](https://github.com/vercel/next.js/discussions/48427).) **MED**
2. **`X-Accel-Buffering: no` and `no-transform`** — proxies and compression will
   otherwise buffer.
3. **Heartbeat every ~2 s of silence** — Vercel documents that it sends HTTP/2
   PING frames on idle long responses but that HTTP/1.1 has no equivalent and
   intermediaries may close the connection.
4. **Self-close at 280 s.** Hobby recycles every connection at 300 s regardless;
   closing first means `EventSource` reconnects with `Last-Event-ID` instead of
   the client seeing a 504.

**The database is the message bus.** A monotonic `seq` column on a
`workspace_event` table, indexed, so each poll is an index range scan returning
zero rows most of the time. This sidesteps the entire cross-instance fan-out
problem — no Redis relay, no instance-id echo suppression, none of the machinery
in Vercel's own reference guides — because every instance reads the same table.
And we already need the database.

**Then spend the memory budget deliberately**, because §6's 180 instance-hours
is the real ceiling:

- **Close the stream when the tab is hidden** (`document.visibilitychange`) and
  reopen on focus. This single behaviour is what makes the budget survivable: an
  abandoned tab costs nothing.
- Close after N minutes with no user interaction, with a "Reconnect" affordance.
- One stream per browser tab, not one per component.

### Graceful fallback that still feels live

The fallback is not a downgrade path we hope never to use — on Hobby it is where
a lot of sessions will actually run, so it has to feel acceptable.

- **`useOptimistic` + Server Actions for the acting user.** The person who drags
  a card sees it move instantly, before any round trip. This is the majority of
  the perceived "liveness" in Linear and it costs nothing.
- **`updateTag()` in the Server Action** (Next 16, §1) for read-your-writes on
  the mutated data, and **`refresh()`** to pull the router.
- **Cursor polling when SSE is unavailable or the tab is backgrounded:**
  `GET /api/changes?since=<seq>`, **5 s** when visible, **30 s** when hidden,
  returning an empty body when nothing changed.

Why 5 s and not 3 s — the arithmetic, derived from Vercel's published unit costs
(**not** quoted from Vercel; they publish no polling guidance):

| Interval | Requests per user-hour | User-hours to 1M invocations | User-hours to 4 CPU-hours @50 ms/poll |
|---|---|---|---|
| 3 s | 1,200 | 833 | **240** |
| 5 s | 720 | 1,389 | **400** |
| 10 s | 360 | 2,778 | **800** |
| 30 s | 120 | 8,333 | 2,400 |

**Active CPU binds long before invocations do.** Five people using the app an
hour a day is 150 user-hours a month — comfortable at 5 s. One tab left open 24/7
is 720 user-hours and is not. Keep the handler trivial (one indexed query, no
serialising of the whole board) because I/O wait is free and CPU is not.

**Decision: SSE from a Node-runtime Route Handler with the database as the fan-out bus — cursor-based, heartbeat every 2 s, self-closing at 280 s, and closed entirely while the tab is hidden — falling back to 5 s/30 s cursor polling, with `useOptimistic` plus `updateTag()` making the acting user's own changes instant regardless** — because it needs no second account or provisioning step, it is immune to the cross-instance fan-out problem that breaks in-memory WebSocket rooms, and closing on tab-hide is the only way the 360 GB-hour provisioned-memory budget survives contact with real users.

2026-12-11. `gpt-5.2-chat-latest` and `gpt-5.3-chat-latest` shut down 2026-08-10
and are already dead.

Minimal request — required fields are just `model` and `input`:

```jsonc
{
  "model": "gpt-5.6-luna",
  "instructions": "You are an issue-tracker assistant. Be terse.",
  "input": "Summarise this thread: …",
  "max_output_tokens": 800,
  "reasoning": { "effort": "low" }
}
```

`instructions` is the system/developer message. `max_output_tokens` **includes
reasoning tokens**. `reasoning.effort` accepts
`none | minimal | low | medium | high | xhigh | max`, defaulting to `medium` on
GPT-5.6.

Response — `output_text` is an **SDK-only convenience aggregate and is not in the
raw JSON**. From raw HTTP you must walk the `output` array, and you must not index
`output[0]` because reasoning items and tool calls occupy slots in it:

```jsonc
{
  "id": "resp_…", "object": "response", "status": "completed", "model": "gpt-5.6",
  "output": [
    { "type": "message", "role": "assistant", "status": "completed",
      "content": [{ "type": "output_text", "text": "…", "annotations": [] }] }
  ],
  "usage": { "input_tokens": 36, "output_tokens": 87, "total_tokens": 123,
             "output_tokens_details": { "reasoning_tokens": 0 } }
}
```

Streaming (`"stream": true`) is SSE with 54 event types; the ones that matter:

```
event: response.created            data: {"type":"response.created","response":{…}}
event: response.output_item.added  data: {…,"item":{"type":"message","role":"assistant","content":[]}}
event: response.output_text.delta  data: {"type":"response.output_text.delta","delta":"Hi","item_id":"msg_…","output_index":0,"content_index":0,"sequence_number":5}
event: response.output_text.done   data: {"type":"response.output_text.done","text":"Hi there!"}
event: response.completed          data: {"type":"response.completed","response":{…}}
```

Terminal events are `response.completed` / `response.failed` /
`response.incomplete`, plus a bare `{ "type": "error", … }`.

SDK: `openai@7.4.0`, zero dependencies, `engines: node >= 22`, runs on Node,
Bun, Cloudflare Workers and the Vercel Edge runtime. Streaming either as a raw
async iterator (`responses.create({stream:true})`) or via
`responses.stream({...})` with typed `.on()` listeners and `await
stream.finalResponse()`. The constructor **throws in a browser** unless
`dangerouslyAllowBrowser: true` — a guardrail, and we will never set it.

**Caveat, unverified:** reported behaviour (community threads + framework issue
trackers, not official docs) is that GPT-5.x rejects `temperature`/`top_p` with a
400 unless `reasoning.effort` is `"none"`. The OpenAPI spec documents the
parameters with no restriction note. **LOW.** The safe rule, which we adopt: do
not send `temperature` to `gpt-5.6-*`.

### 7c. The design consequence: `temperature` does not belong in the port

Both providers' current flagships either hard-reject sampling parameters
(Anthropic: documented 400) or are reported to (OpenAI: unverified 400). A
provider-agnostic interface with `complete(prompt, { temperature })` would
therefore be a **400 generator** — the one option every "LLM abstraction" blog
post puts first is the one option neither current model accepts.

So the port exposes **`effort`**, which both vendors do support, and maps it:

| Port `effort` | Anthropic | OpenAI |
|---|---|---|
| `'low'` | `output_config.effort = 'low'` | `reasoning.effort = 'low'` |
| `'medium'` | `output_config.effort = 'medium'` | `reasoning.effort = 'medium'` |
| `'high'` | `output_config.effort = 'high'` | `reasoning.effort = 'high'` |

### 7d. The port

```ts
// src/ports/ai.ts  — no vendor types leak across this boundary
export interface AiMessage { role: 'user' | 'assistant'; content: string }

export interface CompleteOptions {
  system?: string
  maxOutputTokens?: number
  /** Deliberately not `temperature` — see §7c. */
  effort?: 'low' | 'medium' | 'high'
  signal?: AbortSignal
}

export interface AiUsage { inputTokens: number; outputTokens: number }

export interface AiCompletion {
  text: string
  model: string
  usage: AiUsage
  /** True when the provider declined rather than answered. */
  refused: boolean
}

export abstract class AiConnector {
  abstract readonly id: 'anthropic' | 'openai' | 'disabled'
  /** False when no key is configured. Callers branch on this, never on env. */
  abstract readonly available: boolean

  abstract complete(messages: AiMessage[], options?: CompleteOptions): Promise<AiCompletion>
  abstract stream(messages: AiMessage[], options?: CompleteOptions): AsyncIterable<string>
}
```

`stream` yields plain text deltas. Both vendors' SSE shapes collapse to that, and
keeping vendor event objects out of the port is what makes the two adapters
substitutable.

**Anthropic adapter** — the shape, with the two traps handled:

```ts
class AnthropicConnector extends AiConnector {
  readonly id = 'anthropic' as const
  readonly available = true

  async complete(messages: AiMessage[], o: CompleteOptions = {}): Promise<AiCompletion> {
    const res = await this.client.messages.create({
      model: this.model,                       // ANTHROPIC_MODEL ?? 'claude-opus-5'
      max_tokens: o.maxOutputTokens ?? 4096,
      system: o.system,
      messages,
      ...(o.effort ? { output_config: { effort: o.effort } } : {}),
      // No temperature / top_p / top_k: 400 on every current model.
    }, { signal: o.signal })

    // A safety decline is a 200 with stop_reason "refusal" — check before content.
    if (res.stop_reason === 'refusal') {
      return { text: '', model: res.model, usage: usageOf(res), refused: true }
    }
    // content is a block array and may lead with a thinking block.
    const text = res.content.filter(b => b.type === 'text').map(b => b.text).join('')
    return { text, model: res.model, usage: usageOf(res), refused: false }
  }
}
```

**OpenAI adapter** — same shape; `output_text` is available from the SDK, but the
raw-JSON walk is the honest fallback:

```ts
const res = await this.client.responses.create({
  model: this.model,                           // OPENAI_MODEL ?? 'gpt-5.6-luna'
  instructions: o.system,
  input: toResponsesInput(messages),
  max_output_tokens: o.maxOutputTokens ?? 4096,
  ...(o.effort ? { reasoning: { effort: o.effort } } : {}),
  // No temperature: reported 400 on gpt-5.6 unless reasoning.effort === 'none'.
}, { signal: o.signal })

if (res.status !== 'completed') { /* incomplete / failed — surface, don't pretend */ }
const text = res.output_text
```

**Disabled adapter** — the one that runs by default, because a fresh clone has no
API keys:

```ts
class DisabledConnector extends AiConnector {
  readonly id = 'disabled' as const
  readonly available = false

  async complete(): Promise<AiCompletion> {
    throw new AiUnavailableError(
      'No AI provider configured. Set ANTHROPIC_API_KEY or OPENAI_API_KEY.',
    )
  }
  async *stream(): AsyncIterable<string> { await this.complete() }
}
```

Selection, mirroring the `dbDriver()` discipline from §4 — an unrecognised value
is an error, never a silent fallback:

```ts
export function getAiConnector(): AiConnector {
  const explicit = (process.env.AI_PROVIDER ?? '').trim().toLowerCase()
  if (explicit === 'anthropic') return new AnthropicConnector()
  if (explicit === 'openai') return new OpenAiConnector()
  if (explicit === 'none') return new DisabledConnector()
  if (explicit !== '') throw new Error(`Unknown AI_PROVIDER "${process.env.AI_PROVIDER}".`)

  if (process.env.ANTHROPIC_API_KEY) return new AnthropicConnector()
  if (process.env.OPENAI_API_KEY) return new OpenAiConnector()
  return new DisabledConnector()
}
```

### 7e. Key handling and graceful degradation

- **Keys are read only in `server-only` modules.** `src/adapters/ai/*` starts with
  `import 'server-only'`. Never `NEXT_PUBLIC_ANTHROPIC_API_KEY` — that would ship
  the key to every browser that loads the page.
- The browser never talks to a provider. AI features go through our own Route
  Handler, which streams back to the client. `openai`'s browser guard and
  Anthropic's equivalent are backstops, not the design.
- **Degradation is a UI state, not an exception.** `connector.available` is
  surfaced to the client as a boolean (never the key), so an unconfigured deploy
  renders the AI affordances disabled with "Set `ANTHROPIC_API_KEY` to enable"
  rather than showing a button that throws. Every AI feature must be optional:
  the clone is fully usable with `AI_PROVIDER=none`.
- Rate limits and refusals surface as toasts, not crashes. Both SDKs default to 2
  retries with exponential backoff; leave that on and do not add a second retry
  layer on top.
- **Per-request cost ceiling:** cap `maxOutputTokens` server-side. With
  `claude-opus-5` at $25/1M output, an uncapped 128K-token response is ~$3.20 in
  one click.

**Decision: an abstract `AiConnector` port with `complete()` and `stream()` exposing `effort` rather than `temperature`, implemented by an Anthropic adapter (`@anthropic-ai/sdk`, default `claude-opus-5`), an OpenAI adapter (`openai`, Responses API, default `gpt-5.6-luna`), and a disabled adapter selected when no key is present** — because both vendors' current flagships reject sampling parameters, and because a clone with no API keys must render the AI features as visibly disabled rather than throwing.

## 8. Deployment to Vercel free

### The steps

1. **Push to GitHub, import the repo in Vercel.** Framework detection finds
   Next.js; no build settings need changing. Build command `npm run build`,
   output `.next`, install `npm install` — all defaults.
2. **Add the database from the Vercel Marketplace** (Storage → Neon → Free). This
   provisions the Neon project *and* injects `DATABASE_URL`,
   `DATABASE_URL_UNPOOLED`, `PGHOST`, `PGUSER`, `PGPASSWORD`, `PGDATABASE` into
   the project's environment. **This is the step that makes the deploy story
   short** — there is no connection string to copy.
3. **Set the two required app variables** (see the table below):
   `BETTER_AUTH_SECRET` and `NEXT_PUBLIC_APP_URL`.
4. **Override the Build Command** to run migrations first (next section).
5. Deploy. Optionally add `ANTHROPIC_API_KEY` or `OPENAI_API_KEY` later — the app
   runs without them, with the AI features visibly disabled.

### Migrations, with no shell on the server

This is the question the platform makes awkward, and there are four answers.
Three of them are wrong:

| Approach | Verdict |
|---|---|
| Migrate on first request, guarded by an advisory lock | **No.** It runs once per cold start from however many instances happen to be warming, it puts DDL on the request path, and it makes the first user of a cold deployment wait for a schema migration. |
| A protected `/api/admin/migrate` route with a shared secret | **No** as the primary. It is a manual step that will be forgotten, and it leaves a DDL-executing endpoint permanently exposed. Fine as a break-glass. |
| `vercel env pull` + run `drizzle-kit migrate` from a laptop | Works, but it is a manual step outside the deploy, so schema and code can be out of sync in production for as long as someone takes to remember. |
| **Run migrations in the build command** | **Yes.** |

Build machines have network access and the project's environment variables, and
Hobby allows only **one concurrent build**, so two migrations can never race.
Best of all, a failed migration **fails the build**, so a deployment whose schema
did not apply never goes live — fail-fast, in the one place where failing fast is
free.

Vercel dashboard → Settings → Build & Development Settings → Build Command:

```bash
npm run db:migrate && npm run build
```

where `scripts/migrate.ts` uses the **direct** URL:

```ts
// scripts/migrate.ts
import { neon } from '@neondatabase/serverless'
import { drizzle } from 'drizzle-orm/neon-http'
import { migrate } from 'drizzle-orm/neon-http/migrator'

const url = process.env.DATABASE_URL_UNPOOLED ?? process.env.DATABASE_URL
if (!url) throw new Error('No DATABASE_URL — refusing to build without a database.')

await migrate(drizzle(neon(url)), { migrationsFolder: './drizzle' })
```

Three caveats to design around:

- **`drizzle-kit` must be reachable at build time.** Vercel installs
  `devDependencies` during the build, so a devDependency is fine — but the script
  above imports the *runtime* migrator from `drizzle-orm`, which is a production
  dependency, so it does not depend on that behaviour at all.
- **Preview deployments run this too**, against the same free database, because
  Vercel injects the same env vars into preview. For a demo clone that is
  acceptable; if it stops being acceptable, gate on
  `VERCEL_ENV === 'production'` and use a separate Neon branch for previews (the
  free plan allows 10 branches per project).
- **Migrations must be forward-only and additive.** There is no rollback story
  here, and a destructive migration that fails halfway leaves a free-tier
  database in a state you will fix by hand.

### `vercel.json`

Strictly, **none is required** — Next.js is zero-config on Vercel. One is worth
adding anyway, for three things that are otherwise invisible:

```jsonc
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "framework": "nextjs",

  // Hobby is single-region; iad1 is the default. Stated explicitly so that
  // changing it is a deliberate edit rather than a surprise.
  "regions": ["iad1"],

  // Fluid compute is on by default for projects created after 2025-04-23.
  // Stated so an older project imported here does not silently fall back to
  // the 10s/60s duration table.
  "fluid": true,

  "functions": {
    // The SSE endpoint wants the full Hobby ceiling.
    "app/api/stream/route.ts": { "maxDuration": 300 },
    // Everything else should be nowhere near it. A 300s default on a route
    // that hangs would burn the provisioned-memory budget for nothing.
    "app/api/**/route.ts": { "maxDuration": 15 }
  },

  // Hobby allows ONE cron per day, fired within a ±59-minute window.
  // Session/invite cleanup is the only thing that fits.
  "crons": [{ "path": "/api/cron/cleanup", "schedule": "0 4 * * *" }]
}
```

The `maxDuration` values can equivalently be `export const maxDuration = 300` in
the route segment; prefer the segment export for routes and keep `vercel.json`
for the plan-level facts.

**Do not put a more frequent cron than daily in here.** A `*/5 * * * *`
expression **fails at deploy time** on Hobby with "Hobby accounts are limited to
daily cron jobs" — and it would not have helped anyway, since a ±59-minute
firing window is not a realtime tick.

### Free-tier limits that will actually matter

| Limit | Hobby | Why it matters here |
|---|---|---|
| Function duration | 300 s, not raisable | Caps every SSE connection (§6) |
| **Provisioned memory** | **360 GB-hrs ≈ 180 instance-hours/month** | **The binding constraint.** Long-lived connections bill for wall-clock time, not CPU |
| Active CPU | 4 CPU-hours | Binds polling before invocations do (§6) |
| Invocations / edge requests | 1M each | Generous; not the limit you hit |
| Fast Data Transfer | 100 GB | Return empty bodies on no-change polls |
| Regions | 1 (`iad1`) | Everyone outside North America pays the latency |
| Cron | 1×/day, ±59 min | Cleanup only |
| Deployments | 100/day, 1 concurrent build, 45 min max | 1 concurrent build is what makes build-time migration safe |
| **Over-limit behaviour** | **Project paused, 503, up to 30 days** | No overage billing. Budget headroom, don't plan to the line |
| Commercial use | **Prohibited** | A team actually using this for work needs Pro |

⚠️ **Unverified:** no Hobby allowance for ISR reads/writes is published anywhere;
no monthly build-minutes cap for Hobby is documented (third-party claims of "100
min" and "6,000 min" conflict and neither is sourced to Vercel); Vercel Queues
and Blob Hobby allowances are not in the Hobby table.

### One more guard worth shipping

The `dbDriver()` function in §4 already refuses to boot on Vercel without a
`DATABASE_URL`. Add the auth equivalent: refuse to boot in production with a
missing or default `BETTER_AUTH_SECRET`. A deployment that silently signs
sessions with a placeholder is worse than one that will not start.

**Decision: import the repo, install Neon from the Vercel Marketplace so the connection strings are injected rather than pasted, run `npm run db:migrate && npm run build` as the Build Command so a failed migration fails the deploy, and ship a small `vercel.json` that pins the region, states `fluid: true`, caps non-streaming routes at 15 s, and carries the one daily cron Hobby allows** — because Hobby's single concurrent build makes build-time migration race-free, and because the provisioned-memory budget makes an unbounded default `maxDuration` a real cost rather than a harmless default.

`browser.newContext()` instances inside a single test — **not** two Playwright
workers, which would fight over the PGlite handle.

### `.gitignore` additions

```gitignore
# Local PGlite database. Its whole point is to survive a restart on one
# machine; it is not something to share between them. Deleting it is always
# a safe recovery from a corrupted WAL.
.data/
```

**Decision: pin `next`/`react`/`react-dom`/`eslint-config-next` to the exact versions the sibling projects use, carry their `tsconfig.json`, `postcss.config.mjs`, `vitest.config.mts` and `playwright.config.ts` across with only the PGlite-specific changes noted, and keep both AI SDKs as `optionalDependencies` behind dynamic imports** — because the only new configuration this project needs over its siblings is `serverExternalPackages: ['@electric-sql/pglite']`, and everything else is a solved problem in the same repo.

## Environment variables

The governing rule: **an empty environment must produce a working app.** Every
variable below is either optional, or required *only* in production — and the two
that are required in production fail the boot loudly rather than degrading.

| Name | Required? | Default | What it does |
|---|---|---|---|
| `DATABASE_URL` | **Required on Vercel**, optional locally | *(unset — selects PGlite)* | Neon **pooled** connection string. Its presence is what selects the `neon` driver. Missing it on Vercel is a fatal boot error (§4), because the alternative is a per-instance ephemeral database that silently breaks collaboration. Injected automatically by the Vercel Marketplace Neon integration. |
| `DATABASE_URL_UNPOOLED` | Required for migrations against Neon | falls back to `DATABASE_URL` | Neon **direct** connection string (`-pooler` removed from the host). Used by `scripts/migrate.ts` and `drizzle-kit`; PgBouncer transaction mode breaks DDL tooling. Also injected by the Marketplace integration. |
| `DB_DRIVER` | No | *(inferred)* | Force `pglite` or `neon`. An unrecognised value is a startup error, never a silent fallback. Escape hatch for pointing local dev at a real Neon branch. |
| `PGLITE_DATA_DIR` | No | `.data/pglite` | Where the local embedded Postgres persists. Set to `''` for a purely in-memory database (what the test suite does). |
| `BETTER_AUTH_SECRET` | **Required in production** | dev-only placeholder | Signs session cookies and the cookie cache. Generate with `openssl rand -base64 32`. Boot fails in production if unset or still the placeholder. |
| `NEXT_PUBLIC_APP_URL` | **Required in production** | `http://localhost:3000` | Public origin. Used as Better Auth's `baseURL`, for CORS/trusted origins, and to build invite links — which must be absolute because they get pasted into other apps. On Vercel set it to the production domain; `VERCEL_URL` changes per deployment and is not a substitute. |
| `AI_PROVIDER` | No | *(inferred from keys)* | `anthropic` \| `openai` \| `none`. Unrecognised values are a startup error. |
| `ANTHROPIC_API_KEY` | No | *(unset — AI disabled)* | Enables the Claude connector. **Server-only. Never prefix `NEXT_PUBLIC_`.** |
| `ANTHROPIC_MODEL` | No | `claude-opus-5` | Model ID. Exact strings only, no date suffix. |
| `OPENAI_API_KEY` | No | *(unset — AI disabled)* | Enables the GPT connector. Server-only. |
| `OPENAI_MODEL` | No | `gpt-5.6-luna` | Model ID. Do not pin `gpt-5*` — those shut down 2026-12-11. |
| `AI_MAX_OUTPUT_TOKENS` | No | `4096` | Server-side cost ceiling. At Opus 5's $25/1M output an uncapped 128K response is ~$3.20 per click. |
| `SEED_DEMO_DATA` | No | `true` when the database is empty and the driver is `pglite` | Whether first boot creates the demo workspace, teams, users and issues. Set `false` for an empty start. |
| `PORT` | No | `3000` | Read by `playwright.config.ts` so the test server and `baseURL` can never disagree — several sibling projects share this repo and fight over `:3000`. |

Vercel also injects `VERCEL`, `VERCEL_ENV`, and `VERCEL_PROJECT_PRODUCTION_URL`
automatically; §4's boot guard reads `VERCEL === '1'`.

## What I could not verify

Listed so nobody later mistakes an inference for a fact.

1. **Neon does not delete idle free projects.** Strongly implied (scale-to-zero
   is not pausing; over-limit suspends compute and keeps data) but there is no
   explicit vendor promise either way. **The single most load-bearing unverified
   claim in this document**, since the whole §2 decision turns on it.
2. **Neon cold-start latency.** Neon says "a few hundred milliseconds"; third-party
   measurements range 100–800 ms. No authoritative published figure.
3. **PGlite needs `serverExternalPackages` under Turbopack.** Reported by
   secondary sources, not stated in a Next.js doc page I could quote. Verify on
   the first build; the fallback is a variable-specifier dynamic import.
4. **Better Auth's scrypt parameters (N, r, p, dkLen)** are not in its security
   docs. Read `packages/better-auth/src/crypto/password.ts` in the installed
   version and compare against the OWASP floor before shipping.
5. **OpenAI rejecting `temperature` on `gpt-5.6-*`.** Community and framework
   issue trackers, not official docs; the OpenAPI spec documents the parameter
   with no restriction. We avoid sending it regardless.
6. **Vercel Hobby: ISR read/write allowance, monthly build-minutes cap, Queues
   and Blob allowances, and per-instance Fluid concurrency** are all
   undocumented. The last one is why §6 cannot convert 180 instance-hours into a
   supported user count.
7. **Vercel's behaviour for an already-open stream at the 300 s timeout** is not
   documented; the 504 is, but not what the connected client observes.
8. **`gpt-5.6` has no dated snapshot IDs** in the models pages or the OpenAPI
   enum, so pinning by snapshot may not be possible yet.
9. **Better Auth's `organization` plugin team-role granularity** — I read the
   overview, not the full API. If per-team roles are weaker than Linear's model,
   §5's boundary (own the team tables ourselves) already absorbs it.
