# Risk — Decision Log

Every choice this spec makes, with the reasoning and the evidence file it
rests on. Numbered sequentially; entries are never renumbered or reused.

---

## D1 — The app is titled "Risk", and this file records that RISK is a Hasbro trademark used here for a non-commercial portfolio replica with no copied assets

**Decision.** The app is titled "Risk". This file states plainly that RISK is a trademark of Hasbro, that this project is a non-commercial portfolio replica of SMG Studio's *RISK: Global Domination*, and that it contains no copied Hasbro/SMG artwork, board SVGs, or licensed code.

**Why.** Every sibling replica in this repo is titled after the original it imitates (`research/00-repo-conventions.md` §5's DECISIONS.md convention, following island-empire's own practice), and the map-and-code research turned up a real legal trap worth disclosing explicitly: the Wikimedia "Risk board" SVGs carry CC BY-SA tags despite being traced from a retail Hasbro board the uploader never had rights to (`research/02-maps-and-fan-code.md` §B.5). Recording the trademark and the absence of copied assets on the record keeps the project's legal posture auditable rather than assumed (`research/02-maps-and-fan-code.md` §Legal posture; `research/00-repo-conventions.md` §5).

**Consequence.** Every later decision in this log that touches names, art, or map geometry can point back to this entry instead of re-litigating provenance; the "facts are free, artwork is not" rule governs every map and code decision that follows.

## D2 — `apply(state, action)` is pure and contains no randomness at all, not even a seeded generator

**Decision.** `apply(state, action)` is pure and deterministic — it never calls a PRNG, seeded or otherwise.

**Why.** A PRNG seeded inside client state lets a modified client advance the generator and read the next dice roll before deciding whether to attack, which is the single most attractive and cheapest-to-execute cheat available in an online Risk game (`research/06-online-play-free-tier.md` §5.2). Keeping the engine itself free of randomness is also what makes the layering test (D9) meaningful: "no `Math.random`" is trivial to enforce mechanically only if nothing in the engine ever legitimately needs one.

**Consequence.** Every random outcome — the opening deal, card draws, and every dice roll — must instead arrive as data inside the action that triggers it (D3), decided once by whichever authority is running that turn (the session runner offline, the server online, per D5).

## D3 — Every random outcome is carried inside the action payload, never regenerated by replay

**Decision.** The opening deal and seat order, every card draw, every dice roll, and the Balanced Blitz sample are all carried inside the action payload that produced them, not recomputed from a seed during replay.

**Why.** This makes the action log the single source of truth: replaying `fold(apply, initialState, actions)` reproduces the exact game without re-running any randomness, which is exactly the property the replay-determinism test (D54) and the golden-hash regression suite (D55) depend on (`research/06-online-play-free-tier.md` §5.2; `research/05-bots-and-ai.md` §8). It is the natural complement to D2 — a pure `apply` that still needs to resolve "what did the dice say" has nowhere else to put the answer.

**Consequence.** Every action type that can be random (`attack`, `card_drawn`, `game_started`) carries the concrete outcome in its payload; nothing about the replay depends on which PRNG implementation or seed produced it.

## D4 — A separate pure resolver layer draws from a seeded PCG32 with purpose-tagged sub-streams

**Decision.** A resolver layer outside `apply` (`rollAttack`, `drawCard`, `dealTerritories`) takes an explicit seeded PCG32, and every independent category of randomness draws from its own sub-stream derived by hashing the match seed with a purpose tag and the current turn.

**Why.** Without stream separation, adding or removing a single draw anywhere — a bot-tuning tweak, a new card rule — shifts every subsequent draw and silently invalidates every previously stored replay; this is called out as "the single most important determinism decision in the whole design" (`research/05-bots-and-ai.md` §7.1). Purpose-tagging (`"deal"`, `"turnOrder"`, `"battle"`, `"bot:<playerId>"`, `"cardDeck"`) means a change to how bots decide tie-breaks never touches the battle stream, and vice versa.

**Consequence.** `rngFor(purpose, turn)` is the only way any code path reaches randomness; a reviewer can spot a new, untagged draw in a diff and reject it on sight (`research/05-bots-and-ai.md` §7.2).

## D5 — Offline, the session runner owns the RNG and seed; online, the server owns it and the seed never reaches the browser

**Decision.** Playing offline (solo vs. bots, pass-and-play), the session runner owns the RNG and persists its seed in local state. Playing online, the server owns the RNG entirely, and `games.seed` is never serialised into any response a client can read.

**Why.** The naive design — one seeded PRNG advanced identically by server and client — is wrong for online play specifically because trust is different: if the seed or the PRNG's running state is ever present in the client's copy of the game state, a modified client can run the generator forward and read the next dice roll before deciding whether to attack, which is the single most attractive cheat available and costs nothing to close by simply never sending it (`research/06-online-play-free-tier.md` §5.2). Offline there is no other player to cheat against, so the session runner can safely be the sole authority the way island-empire's own `createSession` already is (`research/00-repo-conventions.md` §2). `games.seed` stays on the `games` row and inside the serverless function purely so a game is reproducible for server-side debugging — it is explicitly kept off the `GameState` type so the response serialiser cannot reach it even by accident.

**Consequence.** Dice, card draws, and the opening deal are resolved server-side online and client-side offline, by the same pure resolver functions (D4), but only one of those two processes ever holds the seed that produced them.

## D6 — A battle consumes exactly one PRNG draw, sampled by inverse-CDF over the full outcome distribution

**Decision.** A battle — however many rounds it would take to resolve — consumes exactly one PRNG draw: the full outcome-probability distribution is computed first, then one uniform float samples the actual result from it by inverse-CDF.

**Why.** This is SMG's own shipped method, `OddsBasedBattle`, and it is the only method Balanced Blitz supports at all, because Balanced Blitz reshapes a whole-battle distribution rather than individual dice (`research/05-bots-and-ai.md` §5.5). It also makes replay and desync detection cheap and uniform: a battle's cost in the log is one row regardless of whether it "lasted" one round or twelve, and the server never has to simulate round-by-round to find out who won.

**Consequence.** `resolveBattle(A, D, cfg, rng)` draws `rng.nextFloat()` once, looks it up against the cached distribution, and returns `(attackerLosses, defenderLosses)` directly — there is no round-loop anywhere in the resolver.

## D7 — Every float that decides a branch is quantised before comparison, to survive `Math.pow`'s cross-engine drift

**Decision.** Any float that decides a branch — most notably the Balanced Blitz CDF walk during inverse-CDF sampling — is rounded to a fixed grid (`round(x · 2^32)`) before being compared against the drawn `u`, rather than compared as a raw float.

**Why.** `Math.pow` is not bit-identical across JavaScript engines, and it appears twice in the Balanced Blitz pipeline — stage 2's win-chance-power exponentiation and stage 4's outcome-power sharpening (`research/05-bots-and-ai.md` §5.5). A replay recorded in V8 could in principle land a hair on the wrong side of a CDF boundary when verified in JavaScriptCore without this, silently breaking cross-browser replay. Quantising the comparison, rather than the underlying math, is cheaper than shipping a custom bit-reproducible `pow`/`ln`/`exp`, and is explicitly the preferred of the three mitigations discussed there.

**Consequence.** The CDF-sampling code path and the bot's own `score > best` comparisons (`research/05-bots-and-ai.md` §7.2) both route through the same quantised-compare helper, so one discipline covers both the dice and the AI.

## D8 — `decideTurn` is pure, lives in the engine, and returns a `TurnPlan` as data rather than performing actions

**Decision.** `decideTurn(view, seat, persona, odds, rng)` is a pure function living inside the engine package. It returns a `TurnPlan` — data describing the whole turn's intended actions — rather than dispatching them itself.

**Why.** A pure, data-returning bot function means solo-vs-bots and bot seats in an online game share one implementation and one test suite, and the UI is free to animate the returned plan at whatever speed it likes without touching the decision logic (`research/05-bots-and-ai.md` §8). It is also what makes a bot's turn replay-verifiable without re-running the bot at all: each attack in the plan is declared, and its resolution still consumes exactly one PRNG draw when it is actually applied (D6), so the plan itself needs no randomness to produce.

**Consequence.** The server's lazy tick (D13) calls `decideTurn`, then feeds each resulting action through the same `apply` every human action goes through; `decideTurn` is re-entered after each battle resolves so an adaptive attack chain can react to how the previous attack went, rather than committing to a conditional plan up front.

## D9 — A build-failing layering test bans React/Next/zustand/zod, sibling layers, and non-deterministic calls inside `src/engine`

**Decision.** A build-failing layering test, copied in shape from super-smash and island-empire, walks `src/engine/**` off disk, strips comments and string literals, and fails the build on any import of `react`/`react-dom`/`next`/`zustand`/`zod`, any import of a sibling top-level layer, any relative import that escapes `src/engine/`, any call to `Math.random`/`Date.now`/`performance.now`/`new Date`/`crypto.`, and any reference to `window`/`document`/`localStorage`/`navigator`/`fetch(`/`requestAnimationFrame`/`process.env`. The test also unit-tests itself.

**Why.** This is the mechanical enforcement of D2 and D4 — a purity rule nobody checks rots the first time a deadline-pressed change calls `Math.random()` for "just a quick blunder roll", and island-empire's own 214-line `layering.test.ts` is proof the pattern catches real violations in a sibling codebase of comparable size (`research/00-repo-conventions.md` §2). The online-play lane independently converges on the identical requirement for the same engine (`research/06-online-play-free-tier.md` §5.1), which is reassuring cross-checking rather than a second decision. super-smash's own variant additionally bans trigonometric `Math.*` calls for its physics engine, which Risk's turn-based rules do not need, so the banned-call list is retuned rather than copied verbatim.

**Consequence.** Any engine code that genuinely needs a timestamp, a random draw, or the DOM has to go through an injected port instead (the session runner's `now()`/`schedule()` for timing, the `Rng` interface for randomness per D4) — the test makes that boundary unavoidable rather than aspirational.

## D10 — Online play is server-authoritative Option A: an append-only action log behind route handlers, synced by adaptive polling

**Decision.** Online play is Option A from the online-play research: a server-authoritative engine behind Next.js route handlers, an append-only `game_actions` log with contiguous `seq`, adaptive client-side polling, a `204` response on no change, exactly three poll endpoints, every periodic duty performed lazily inside whichever poll arrives next, cookie-based identity, PGlite locally and Neon deployed.

**Why.** Of the four options evaluated — polling, SSE, Supabase Realtime, and Trystero P2P — only this one has a cost model computable inside Vercel Hobby plus Neon's free tier without a second account, and it is the only one whose state survives a refresh or a closed tab, which matters because a turn-based game's sessions last long enough that someone will reload (`research/06-online-play-free-tier.md` §0, §4.1). SSE and Supabase Realtime both win on latency the game does not need (turns last tens of seconds) at the cost of a less predictable or less self-contained budget; Trystero P2P puts the authoritative state in one visitor's tab, which ends the game the moment that tab closes.

**Consequence.** Every other online decision in this log (D11–D17) is a direct elaboration of this one — the polling cadence, the one-poll-does-everything design, the lazy tick, the idempotency scheme, and the cookie-based identity model all follow from "the server owns the state, clients poll for it".

## D11 — Polling runs at 2s on your turn, 4s off it, 5s in the lobby, 15s hidden, stopping after 5 minutes hidden

**Decision.** The client polls at 2,000 ms on your own turn, 4,000 ms on someone else's turn, 5,000 ms browsing the lobby, 15,000 ms with the tab hidden, and stops entirely after 5 minutes hidden — with ±15% jitter and an immediate extra poll on visibility-regain and right after your own successful POST.

**Why.** Stopping when the tab is hidden is the difference between a free Neon database and a dead one: Neon's free tier charges for *awake* wall-clock time regardless of query volume, and a single abandoned tab polling forever at 2s would alone burn 182.5 CU-hours against a 100 CU-hour monthly allowance — 1.8× the whole budget (`research/06-online-play-free-tier.md` §2.1, §4.1). The adaptive mix (faster on your own turn, where latency is most felt; much slower everywhere else) keeps the average invocation cost near 1,100 per player-hour of active play, the number the whole monthly budget is sized against. Jitter prevents four clients in one game from synchronising into a thundering herd against the same row.

**Consequence.** A player who tabs away for a coffee costs the budget almost nothing; a player mid-turn gets a response that feels close to instant even though nothing pushes to them.

---

## D12 — The game poll folds presence, chat, the delta and the lazy tick into one invocation, returning 204 when nothing changed

**Decision.** `GET /api/games/:id?since=<seq>` does five jobs in one request: stamps the caller's presence, runs the lazy tick (expired deadline, bot turn), returns the action-log delta (or a snapshot if the client has fallen behind), returns other seats' presence and the turn deadline, and returns new chat messages — and it returns a bare `204 No Content` when `seq === since`.

**Why.** A design with separate presence, chat, and game polls costs three times the invocations for no added capability, and invocations are one of two co-binding Vercel Hobby limits (`research/06-online-play-free-tier.md` §4.1). The `204` path matters even more than the folding: Active CPU, the other co-binding limit, is charged for JSON serialisation time, not for waiting on the database, so a poll that always returns a full ~4–8 KB state snapshot binds the CPU budget at only 576,000 polls, while a poll that usually returns nothing at all binds at 2,880,000 — a 5× difference from one design choice.

**Consequence.** `ETag: W/"<seq>"` plus `If-None-Match` makes the common "nothing happened" case a cheap string comparison, and the snapshot is only ever sent to a cold client or one that has fallen behind the compaction horizon (`snapshot_seq`).

---

## D13 — Bot turns, timeouts, takeovers and garbage collection all run lazily inside whichever poll arrives next

**Decision.** Bot turns, turn-timer expiry, seat-to-bot takeover, and reaper garbage collection are not background jobs — each runs lazily, inside whichever client's poll happens to arrive next, under a `tick_lease` that prevents two simultaneous polls from both running the same tick, with an `MAX_TICK_ACTIONS ≈ 40` cap per invocation. One daily Hobby cron sweep exists as belt-and-braces insurance only.

**Why.** Vercel Hobby cron can fire at most once per day, so no design that needs anything periodic more often than that can rely on cron at all (`research/06-online-play-free-tier.md` §1.5, §4.5.3). The lazy-tick design turns this constraint into a genuine improvement rather than a workaround: work that only happens while someone is actually watching is strictly better than work that happens on a fixed schedule whether or not anyone benefits from it, and it is free precisely because there is always at least one poll in flight whenever the outcome of that poll would matter to anybody.

**Consequence.** A `MAX_TICK_ACTIONS` cap on a chain of consecutive bot seats means a player watching three bots move in a row sees them resolve across a couple of polls rather than inside one slow request — visibly better than a four-second frozen response, and each step is still a row in the action log (D14).

## D14 — Every timeout, takeover and reconnect is a row in the action log, never a silent side effect

**Decision.** A missed turn deadline, a seat flipping to a bot after two missed turns, and that seat flipping back to a human on reconnect are each an explicit row appended to `game_actions`, never an un-logged side effect of some other request.

**Why.** This is what lets every client learn about a takeover exactly the way it learns about a dice roll — by folding the log — rather than needing a second, special-cased notification channel (`research/06-online-play-free-tier.md` §4.5.4). It is also what keeps a replay faithful: replaying from `seq = 0` must reconstruct the same sequence of human-vs-bot seat ownership that actually happened, and that is only possible if every ownership change is itself a logged action with its own `state_hash`.

**Consequence.** The `game_players.kind` column (`human`/`bot`) only ever changes as a consequence of applying a `seat_to_bot`/`seat_to_human` action through the same pure `apply`, so a client replaying the log needs no special-casing to render "Napoleon went away — the bot took over".

## D15 — `clientActionId` is minted once per intent and a duplicate POST returns 200 with the already-recorded action

**Decision.** `clientActionId` is minted once, at the moment of the player's intent (the click), reused verbatim on every retry of that same POST, enforced by a unique `(game_id, client_action_id)` index — and a duplicate submission returns `200` with the action that was already recorded, not an error.

**Why.** A network retry must be indistinguishable from a slow success, because a double-click or a flaky connection will produce exactly the retry this design has to tolerate; a resend that mints a *new* id, by contrast, is a second, distinct attack and must not be treated as idempotent (`research/06-online-play-free-tier.md` §5.4). Generating the id at the point of intent rather than the point of send is the entire value of the rule — anything else reopens the door to double submission.

**Consequence.** The handler catches Postgres's `23505` unique-violation on that index and answers `200` with the already-recorded `seq`, and the client's own `pendingActions` entry carries the same id so even a response that is lost twice converges to the same outcome.

---

## D16 — Every action carries a canonical `state_hash`, and a client mismatch drops local state and refetches rather than reconciling

**Decision.** Every row in `game_actions` carries `state_hash`, the hash of the state immediately after that action was applied, computed over a canonical serialisation (sorted keys, integers not floats, no `undefined`). A client that applies an action and gets a different hash does not attempt to reconcile — it drops its local state, refetches the authoritative snapshot, and reports the mismatch.

**Why.** A desync is, by construction, a bug in `apply` (the same pure function runs on client and server from the same log), and the only useful response to a bug is one that is loud and recoverable rather than one that tries to paper over it with heuristics that might themselves be wrong (`research/06-online-play-free-tier.md` §5.5). super-smash already carries a `hash.ts` for exactly this purpose, so the pattern is proven in a sibling project, not invented for this one.

**Consequence.** `hashState` needs its own property test — `∀ state. hashState(state) === hashState(roundTrip(state))` — because a hash sensitive to key order would manufacture false desyncs out of nothing worse than JSON serialisation order.

## D17 — Identity is a chosen display name behind a server-minted httpOnly cookie, released 2 minutes after leaving, with a 4-letter lobby code **[ours]**

**Decision.** There are no accounts. A visitor picks a display name on arrival (or accepts a generated `<Adjective> <Noun> <NN>` default of our own wording), the server mints the actual secret and sets it as an `httpOnly`, `Secure`, `SameSite=Lax` cookie, the name is held only while the player is live and released two minutes after they leave unless they are seated in a game or lobby, an online-players list shows who else is around, and a lobby is addressed by a 4-letter code drawn from a 24-letter alphabet excluding `I` and `O` (24⁴ = 331,776 codes).

**Why.** RGD itself has no custom usernames at all — it only supports a name synced once from a linked platform account — so this entire identity model is our own addition, not a replication of anything RGD does (`research/06-online-play-free-tier.md` §4.5.2; `research/03-ux-flow-modes-dialog.md` §6). The server minting the secret, rather than the client generating one, means nothing sensitive is ever reachable from JavaScript — `localStorage` holds only the display name and colour, purely for instant first paint. The 2-minute release window and the "never reaped while seated" rule both come directly from the reap query in the session route: a name is yours while you are live, and a name is never yanked out from under a seat that still refers to you, however long you have been away. The 4-letter, no-`I`/`O` lobby-code alphabet is lifted verbatim from super-smash's own room-code generator, chosen there because it is "short enough to say in one breath, and free of the pairs that get misheard" (`research/06-online-play-free-tier.md` §4.4).

**Consequence.** `POST /api/session` is the entire auth system — no password, no email, no third-party library — and `DELETE /api/session` cleanly releases both the cookie and the name.

## D18 — Reinforcements are `max(3, floor(territories/3))` plus the classic continent bonuses, checked at the owner's turn start

**Decision.** `reinforcements = max(3, floor(territories_owned / 3))`, plus the classic continent bonuses North America +5, South America +2, Europe +5, Africa +3, Asia +7, Australia +2, checked at the start of the owning player's turn.

**Why.** The 2003 Hasbro rulebook and SMG's own "WIKI – Draft"/"WIKI – Conquering Continents" support articles agree on every one of these numbers verbatim, down to matching the worked examples ("16 territories / 3 = 5 troops... cannot be less than 3") and the exact continent figures (`research/01-core-rules.md` §2.2, §2.3) — two independent, high-authority sources confirming the same formula is as solid as this research gets.

**Consequence.** Continent ownership is evaluated once, at the owner's turn start, not continuously — losing a territory mid-opponent's-turn costs you the bonus only from your *next* draft onward, matching the rulebook's "if you remain in control... by the beginning of your next turn" wording exactly.

## D19 — Fixed card bonuses are 4/6/8/10 with a +2-per-turn territory cap; Progressive is 4/6/8/10/12/15 then +5 per set forever

**Decision.** Under Fixed, a matched set is worth 4 (three Infantry), 6 (three Cavalry), 8 (three Artillery), or 10 (one of each, or a Wild substituting for any type); any traded card depicting a territory you currently occupy adds +2, capped at +2 total per turn. Under Progressive, the first six sets are worth 4/6/8/10/12/15, and every set after that adds a flat +5 forever (20, 25, 30, …).

**Why.** Two independent, high-authority sources — the 2003 Hasbro rulebook and SMG's own "WIKI – Card Trading" article — agree verbatim on every one of these values, including the exact "+5 per set after the sixth" rule and the territory-match bonus's own +2 cap (`research/01-core-rules.md` §3.4, §3.5). The rulebook's separate, optional "Rules Variations for RISK Experts" slower-growing scheme (4, 5, 6, 7…) is explicitly not what RGD exposes as "Progressive" and is deliberately not implemented, to avoid confusing the two.

**Consequence.** The territory-match +2 is capped once per turn regardless of how many traded cards happen to match owned territory, and Fixed/Progressive are two distinct, selectable schemes rather than one with a toggle on the escalation.

## D20 — The three card-timing branches — forced trade, reward draw, inherited elimination hand — are modelled as distinct rules

**Decision.** Three card-timing branches are modelled as genuinely distinct code paths: holding 5 or more cards at the start of your turn forces at least one trade-in (and allows a second if you still qualify); drawing your own end-of-turn battle-reward card up to 5 or 6 cards forces nothing until your *next* turn's start; and inheriting an eliminated player's hand mid-turn, if that brings your total to 6 or more, forces an *immediate* trade-down to 4 or fewer, one set at a time, stopping as soon as you reach 4, 3, or 2.

**Why.** The rulebook states this three-way distinction explicitly and precisely, including the exact wording that a draw landing on exactly 6 still "must wait until your next turn," while an elimination landing on 6+ forces trading *immediately* — and it is flagged in its own source as "the single most important and easy-to-get-wrong card-timing rule in the whole ruleset" (`research/01-core-rules.md` §3.6, §3.7, §8). No RGD-specific source contradicts the rulebook's version of this edge case, so it is implemented verbatim pending in-app verification.

**Consequence.** The engine needs three separate trigger checks — at turn start, after the end-of-turn reward draw, and immediately upon absorbing an eliminated player's hand — rather than one generic "check card count, trade if ≥5" rule, because only the elimination branch forces an in-turn interrupt.

## D21 — Dice are textbook: attacker ≤3, defender ≤2, highest-vs-highest, ties to the defender, attack only from ≥2 armies

**Decision.** The attacker rolls up to 3 dice (needing one more army than dice rolled), the defender rolls up to 2 (needing 2+ armies to roll a second), highest-vs-highest and second-vs-second are compared, ties go to the defender, the attacker loses at most 2 armies per roll, and an attack may only launch from a territory holding at least 2 armies. The six single-roll outcome distributions (3v2, 3v1, 2v2, 2v1, 1v2, 1v1) are the exact fractions derived by exhaustive enumeration.

**Why.** SMG's own `risk-dice` GitHub README prints `AttackLossChances[2] = 0.292566872427984` for a standard 3v2 round, and independent exhaustive enumeration of all 7,776 outcomes gives `2275/7776 = 0.2925668724279835` — an exact match, which is first-party confirmation that RGD's shipped code uses the textbook rules rather than some house variant (`research/01-core-rules.md` §4.1; `research/05-bots-and-ai.md` §4.1). The same fractions independently appear in Osborne's peer-reviewed 2003 correction of Tan's 1997 Markov-chain analysis, so three unrelated derivations — our own enumeration, SMG's shipped float, and a published mathematics paper — agree.

**Consequence.** Every downstream battle-odds table (D22) and every AI win-probability check is built on these six distributions as ground truth, with no fudge factor anywhere in the dice math itself.

## D22 — Full-battle odds come from a precomputed O(A·D) DP table up to 128, with a fitted logistic beyond it

**Decision.** Full-battle win probability `W[A][D]` (A excludes the one army that must stay behind) is computed by an O(A·D) dynamic program over the single-roll distributions, precomputed as a `Float32Array` for `A, D ≤ 128`, one table per `(attackDice, defendDice, favourDefenderOnDraw)` triple; beyond the table, a fitted logistic `σ((A − 0.860·D)/(0.630·√(A+D)))` approximates it.

**Why.** The DP matches SMG's own published non-trivial worked example — "the win chance for attacking 800 zombies with 300 troops," which SMG prints as `0.8897331` and this DP returns as `0.8897332621740284`, agreement to 7 significant figures — so this is the formulation RGD itself uses, not an approximation of it (`research/05-bots-and-ai.md` §4.3). Building the whole table costs only 2.07 ms and 80 KiB, independently measured, versus an alternative of clamping out-of-range indices into the table, which measures a maximum error of 0.8565 — catastrophically wrong, because it destroys the troop *ratio* the whole signal depends on — while the fitted logistic's maximum error over the same extrapolation band is only 0.0318 (`research/05-bots-and-ai.md` §4.5).

**Consequence.** A single shared table, rather than a per-query Monte-Carlo simulation, backs both the Blitz Win Chance readout and every bot's attack-gate decision, and it costs no PRNG draws to consult (unlike simulation, which would also break determinism).

## D23 — Balanced Blitz is implemented as SMG's exact 4-stage reshape, written from the behavioural spec rather than their source

**Decision.** Balanced Blitz is implemented as the exact 4-stage reshape of the true outcome distribution — win-chance cutoff (0.05), win-chance power (1.3), outcome cutoff (0.10), outcome power (1.8) — using SMG's published default constants, written entirely from the behavioural specification derived by reading and independently reimplementing their algorithm description, never by copying or vendoring SMG's `risk-dice` source, which is licensed for internal evaluation only.

**Why.** SMG's own README documents the four-stage pipeline precisely enough that a clean-room reimplementation reproduces both of their published worked examples to all 16 printed digits: a capital-assault loss-of-exactly-12 probability matches `0.0222128001707278`/`0.0100282888709122` exactly for True Random and Balanced Blitz respectively, and the "fewest attackers for ≥80% Balanced Blitz win chance against 50 defenders" example correctly comes out to 49 (`research/05-bots-and-ai.md` §5.2, §5.3). That level of agreement means the specification is complete enough to build from without ever reading or copying the C# source text itself, which the licence forbids reproducing.

**Consequence.** Stage 1 alone explains the long-standing community complaint that "5 vs 1 wins 100%" — any attack whose true win chance already exceeds 95% snaps to a guaranteed win — and that behaviour is therefore intentional parity, not a bug to fix.

## D24 — Balanced Blitz distributions are computed lazily and memoised, never tabulated in full at init

**Decision.** Balanced Blitz win-chance and outcome distributions are computed lazily, memoised per `(A, D)` pair the first time they are actually queried, rather than built as a complete table at engine startup the way the True Random table (D22) is.

**Why.** Unlike True Random, Balanced Blitz needs the *full* outcome distribution for every `(A, D)` pair it touches (because the reshape operates on the whole distribution, not just the final win probability), and that full-distribution computation is itself O(A·D) per pair — so a complete 100×100 table costs a measured 199.8 ms, well over any reasonable init budget, while the same table at 32×32 costs only 4.4 ms, and small battles dominate real play (`research/05-bots-and-ai.md` §6). Building it once during a loading screen with a yield between rows, or shipping a precomputed binary asset, are the two acceptable alternatives if lazy memoisation ever proves insufficient.

**Consequence.** The memoisation cache is pure and keyed on the full battle configuration `(A, D, attackDice, defendDice, favourDefenderOnDraw, stopUntil, balanceConfig)`, and — critically — it must never be serialised into a save or a replay, or a cache that happens to be warm on one machine and cold on another becomes a source of replay divergence.

---

## D25 — Bots are given the odds table matching the active dice mode, and Expert exploits a `certainWin` predicate

**Decision.** A bot is always given the win-chance table for the dice mode actually active in the match (True Random or Balanced Blitz), never the other one by default, and the Expert tier additionally exploits an explicit `certainWin` predicate (`W_bb ≥ 1 − ε`) when planning a conquest chain.

**Why.** Giving a bot the True Random table while Balanced Blitz is active is measured to make it underestimate its own odds by up to 14 percentage points (a 20v15 attack is 86.04% under True Random but exactly 100% under Balanced Blitz), which is a correctness bug in the bot, not a tuning choice (`research/05-bots-and-ai.md` §5.4). The fixed point of the Balanced Blitz transform sits at exactly 50%, so the attack-gate threshold `A ≥ D+1` itself does not need to change between modes — only the *payoff* estimate for attacks the bot was already going to make does, which is exactly what feeding it the right table corrects.

**Consequence.** The bot's odds-table lookup is parameterised by the match's active dice mode at construction time, and Expert specifically treats any attack past the `certainWin` threshold as risk-free for the purposes of chaining further conquests in the same turn.

---

## D26 — We use the exact DP at every battle size, deliberately more accurate than SMG's large-battle regression fallback

**Decision.** The win-chance DP (D22) is used at every battle size our implementation ever needs, rather than switching to a polynomial-regression estimator for large stacks the way SMG's own shipped code does.

**Why.** SMG's own documentation is candid that their large-battle fallback "can result in discrepancies between the game and this code" because the estimation source itself is not provided, while our DP is O(A·D) and measured at 1.80–2.07 ms to build a complete 100–200-entry table — there is no performance reason to accept SMG's known inaccuracy (`research/05-bots-and-ai.md` §5.5).

**Consequence.** This is a deliberate, disclosed divergence from RGD rather than an oversight — our odds readout and our bots will occasionally be *more* accurate than RGD's own at very large troop counts, worth noting precisely so nobody "fixes" it to match RGD's documented imprecision.

---

## D27 — Dice augments are integer `defendDiceBonus`/`attackDicePenalty` summed from active modifiers, never enumerated named modes

**Decision.** Every dice-mode augment — Capitals (+1 defender die), Behind-Wall (+1 defender die), Zombie-attacker (−1 attacker die), Zombie-defender (ties favour the attacker) — is modelled as an integer `defendDiceBonus`/`attackDicePenalty` summed from every currently active modifier, keyed into the odds-table cache by the resulting `(attackDice, defendDice, favourDefenderOnDraw)` triple, rather than as a fixed list of named combat modes.

**Why.** SMG state explicitly that these augments stack — "Human attacking Zombie: Ties favor attacker instead of defender / ... Attacking over Wall: +1 max defender die ... These also STACK!" — so a capital defended behind a wall gives the defender up to 4 dice, which a named-mode enumeration (standard / capital / wall / zombie) would simply never produce as a combination (`research/01-core-rules.md` §4.1; `research/05-bots-and-ai.md` §1.1, §3.2, §4.6). The magnitude is not cosmetic: a 10v10 capital assault drops from 56.76% (standard) to 19.02% (capital) to 5.31% (capital-behind-wall) — a bot or UI using the wrong table there is wrong by tens of percentage points, not a rounding error.

**Consequence.** With `attackDice ∈ {1,2,3}` and `defendDice ∈ {1,2,3,4}` plus two tie rules, the complete set is only 24 round distributions, all trivially precomputable, and every territory simply exposes its own `defendDiceBonus` so capitals and walls share one code path rather than two parallel ones.

---

## D28 — Five bot tiers are labelled exactly as RGD's AI Difficulty, with personas drawn once at match start and stored

**Decision.** Five bot difficulty tiers — Beginner, Easy, Medium, Hard, Expert — are labelled exactly as RGD's own "AI Difficulty" setting, implemented per the tier table in `research/05-bots-and-ai.md` §3.5, with each bot's persona drawn once at match start from the difficulty's persona pool and stored in match state rather than re-derived every turn.

**Why.** SMG's own support article states plainly that difficulty is "a mixture of various 'personas'" and that "some personas are restricted to certain difficulties," i.e. difficulty selects *which characters you might face*, not a single smartness dial — exactly the architecture Lux Delux's `Chimera` bot ("randomly chooses the behavior from other hard AIs") independently converged on under a different name (`research/05-bots-and-ai.md` §1.1, §2.14). Drawing the persona once and persisting it, rather than resampling it, is what lets a replay loaded later reconstruct an identical opponent without re-deriving anything from a possibly-changed heuristic.

**Consequence.** Two Hard games can feel meaningfully different because they happened to draw different personas from the same pool, which is the exact behaviour SMG themselves describe causing players to perceive bots as "inconsistent" when really a persona simply clashed with that player's style.

---

## D29 — Low-tier bots blunder by picking the k-th best move, rather than miscomputing — one code path for every tier

**Decision.** A low-tier bot computes its move scoring exactly as a high-tier bot would, then — with probability `blunderRate` — picks the k-th best candidate instead of the best one. Nothing about the scoring math itself is ever made deliberately wrong.

**Why.** This keeps determinism simple (one scoring function, one extra seeded draw, rather than a second, deliberately-buggy evaluation path to maintain) and avoids the classic failure mode where a "dumb" bot accidentally becomes *stronger* than intended because its simplified evaluation happens to dodge some trap a correct one would walk into (`research/05-bots-and-ai.md` §3.5). Warzone's own production AI independently reaches the same design — weighted-random selection over a scored action set, explicitly because "the AI tends to make similar decisions in similar situations, but will not always make the exact same move" — and its own 1-in-20 deliberately-bad-attack rule is cited as "the single best line in the repo for making a bot feel human" (`research/05-bots-and-ai.md` §2.14).

**Consequence.** `blunderRate` is 0.30/0.12/0.03/0.00 for Easy/Medium/Hard/Expert, consuming exactly one extra seeded draw per decision point, and tuning a tier's difficulty is a one-number change rather than a code fork.

---

## D30 — Expert's extra compute goes into the draft and a one-ply reply check, not into deeper attack search

**Decision.** Expert's additional compute budget is spent on the opening draft (an evaluator over the published Gibson et al. learned weights, plus a short search to the end of the draft only) and on a single-ply "best opponent reply" check during the attack phase — not on deeper multi-ply search of the attack phase itself.

**Why.** Three independent published results converge on the same, counter-intuitive conclusion: Gibson et al. found that holding post-draft play identical while randomising only the draft collapsed an otherwise-strong agent's win rate, Gnecco & Cazenave found their "init-only" variant (a learned draft followed by *random* play) outperformed their full, iteratively-trained agent, and Hahn found the eventual winner of a self-play game is already statistically identifiable 60% of the way through (`research/05-bots-and-ai.md` §2.6, §2.9, §2.15). A ply-2 attack-phase search was separately measured to cost 20–200 ms even restricted to the top 3 candidates each side — borderline against the 100 ms budget — while ply-1 lookahead on the top ~8 candidates comfortably fits inside 10 ms, so the budget is spent where the literature says it matters most, not where intuition points.

**Consequence.** Expert is measurably "smarter" mainly in how it drafts and in catching the single best punishing reply to its own attack, not in simulating several turns ahead, which keeps its worst-case per-turn cost in the single-digit milliseconds.

---

## D31 — Bots see through fog of war only at Expert; lower tiers keep an honest, pessimistically-inflated belief

**Decision.** A bot at Easy, Medium, or Hard maintains an honest, per-bot belief of last-seen troop counts and inflates unknown stacks by a `fogPessimism` factor; only the Expert tier reads true, un-fogged state.

**Why.** SMG state plainly that their real AI "can see the player's troops and factors that into its calculations" under Fog of War at every difficulty — the only admitted information advantage their bots have at all (`research/05-bots-and-ai.md` §1.1). Giving that same edge only to Expert in our implementation is a deliberate, disclosed divergence: it keeps low tiers feeling genuinely fair under fog (where RGD's own low-tier bots quietly cheat) while still matching RGD exactly where it is said to matter most — Expert. Warzone's production AI independently documents the honest alternative in detail (`StatefulFogRemover`/`StatelessFogRemover`, "we have no way of knowing what's there, so just assume the minimum"), which is the model for the lower tiers' belief-tracking (`research/05-bots-and-ai.md` §2.14, §3.2).

**Consequence.** Only Expert needs the un-fogged `BoardView`; every other tier's `decideTurn` call receives the same fog-filtered view a human player would see, with the pessimism inflation substituting for genuine knowledge.

---

## D32 — Fortify is connected-path, one move per turn, with at least one army left behind, and is always optional

**Decision.** Fortify moves any number of troops, minus one left behind at the source, along a path through territories the mover currently owns (a graph-reachability check, not strict single-hop adjacency), once per turn, and can always be skipped entirely. Attacking, unlike fortifying, still requires direct adjacency or an explicit sea route — it never benefits from the same connected-path rule.

**Why.** RGD's own "WIKI – Fortify" article's phrasing ("troops can only travel between connecting territories," with strategic advice about "strengthening your borders... such as the borders of a continent") reads far closer to a multi-hop connected-path move than to the base print rulebook's stricter single-adjacent-hop default, and an independent secondary source describes it the same way — against only the un-RGD-specific rulebook's stricter baseline (`research/01-core-rules.md` §5; `research/03-ux-flow-modes-dialog.md` §2.5). The print rulebook's own *optional* "Rules Variations for RISK Experts" appendix is itself the origin of the connected-path variant, strengthening the case that RGD's digital implementation adopted the variant rather than the baseline rule.

**Consequence.** Fortify needs a BFS/graph-reachability check through the mover's own territories rather than a simple adjacency lookup, which is a meaningfully different (and more expensive) legality check than attacking's.

---

## D33 — Post-conquest troop movement ranges from the dice used in the conquering roll up to source minus one

**Decision.** After conquering a territory, the minimum number of troops that must move in equals the number of dice used in the final, conquering roll (1, 2, or 3); the maximum is every troop in the attacking territory minus the one that must always stay behind.

**Why.** This is stated exactly in the print rulebook ("move in at least as many armies as the number of dice you rolled in your last battle... you must always leave at least one army behind") and SMG's own Blitz form of the same rule independently confirms a minimum of 3 after attacking with 3 or more dice (`research/01-core-rules.md` §4.5; `research/03-ux-flow-modes-dialog.md` §3).

**Consequence.** The slider's bounds are derived from the specific battle just resolved, not from a fixed minimum, so a 1-die conquest and a 3-die conquest present different sliders even on the same territory.

---

## D34 — In-scope modes and modifiers are exactly eleven named systems; everything else is deferred or out of scope

**Decision.** The in-scope modes and modifiers are exactly: World Domination, Percentage Domination, Capitals, Fog of War, Fixed/Progressive cards, Balanced Blitz/True Random, Blizzards, Portals, Manual vs. Auto placement, Max Rounds, Turn Timer (online only), and an Alliances toggle. Zombies, Secret Missions, Secret Assassin, team play, and ranked matchmaking are explicitly out of scope.

**Why.** Every item on the in-scope list is independently sourced to a primary or high-confidence source, while everything excluded is either unverified (Zombies' exact numbers), not actually shipped as a real feature in RGD (team play is roadmap-only per SMG's own developer statements), or purely monetisation infrastructure (ranked's gem/token economy) that has nothing to do with the rules being replicated (`research/01-core-rules.md` §6; `research/03-ux-flow-modes-dialog.md` §2).

**Consequence.** This is the scope boundary every other mode/modifier decision in this log (D27, D35, D56–D62, D75) elaborates — a feature request for Zombies or team play is a scope change against this entry, not a bug against any of them.

---

## D35 — Blizzards, Portals and Capitals are global modifier systems with a per-map count, not per-map rules

**Decision.** Blizzards, Portals and Capitals are each implemented once, as a global modifier system that can be toggled on for *any* map, with each map simply declaring how many blizzards/portals it places; a blizzard tile still counts toward its region's continent bonus.

**Why.** This is how the real catalogue actually works — the map research confirms these are toggles layered onto any of the 134 SMG maps rather than bespoke per-map special rules, which is explicitly called "the highest-leverage feature in the whole catalogue — it multiplies every map you have" (`research/02-maps-and-fan-code.md` §A.1). Implementing them as one system plus a per-map count rather than N bespoke systems is therefore not just simpler, it is the architecturally correct read of how SMG themselves built it.

**Consequence.** Adding a new map to the catalogue never requires writing new blizzard/portal logic — only choosing how many of each it places — and a blizzard-blocked tile is excluded from pathing without being excluded from its continent's ownership check.

---

## D36 — Every map is one JSON file with the SVG path inline per territory, checked by a build-time validator

**Decision.** Every map ships as a single JSON file carrying the SVG `d` path inline per territory (rather than a separate SVG asset the loader has to reconcile against the graph), validated at build time against: adjacency symmetry, no dangling references, every territory has geometry, and every continent's territory list is complete.

**Why.** Keeping geometry inside the same JSON as the graph means one fetch per map and no two-sources-of-truth problem, which matters because every real-world Risk map source examined — TotalRisk, risk-neighborhood, even two of the nine classic-map sources that disagreed — shipped at least one bug a build-time validator of exactly this shape would have caught (`research/02-maps-and-fan-code.md` §B.6). This schema is modelled on `go-risk-it/go-risk-it-frontend`'s data shape (reimplemented independently, not copied, since that repo carries no licence), singled out as "the cleanest data model found" for exactly this reason.

**Consequence.** A malformed map fails the build, not the runtime — nobody discovers a dangling adjacency reference by playing the game and hitting a crash.

---

## D37 — We ship thirteen maps: three licensed real boards, eight generated regional maps, and a seeded generator

**Decision.** Tier 1 ships the Classic world map (verified 42/6/83, Unlicense/Apache-2.0 geometry), World Extended (47/6), and Napoleonic Europe (59/11) as-is, using `sonesson89/TotalRisk`'s existing per-territory SVGs. Tier 3 generates roughly eight more regional maps (Europe, USA, Asia, Africa, South America, Canada, Australia/NZ, a simple world) from public-domain geodata. Tier 4 adds one seeded Voronoi-tessellation map generator for infinite random boards. Total: 13 maps with defensible provenance.

**Why.** This is the only route to 10+ maps that does not depend on unlicensed or copyleft sources — Lux Delux (1,000+ maps), Warzone, TripleA (343 repos), Domination (107 maps), and MapGenie (~120 adjacency graphs that mirror SMG's own catalogue almost exactly) were each individually checked and found unlicensed, proprietary, or copyleft, which is "a firm finding, not a gap in the search" (`research/02-maps-and-fan-code.md` §Recommendation). Classic's adjacency is independently verified by seven of nine machine-readable sources agreeing exactly on all 42 territories and 83 edges, the highest-confidence fact in the entire map lane.

**Consequence.** Nothing beyond these 13 boards can be added without either hand-authoring new geometry the way TotalRisk's own three maps were, or running the Tier 3 geodata pipeline again on a new region — there is no shortcut through any of the catalogues examined.

---

## D38 — We never ship SMG's artwork or the Wikimedia Hasbro-derived board SVGs, even under their CC BY-SA tags

**Decision.** SMG's own map artwork is never shipped, and neither is the Wikimedia "Risk board" SVG family (`Risk_board.svg`, `Risk_game_board.svg`) despite their CC BY-SA licence tags. Facts about the real game — names, graphs, counts, bonuses — are reused freely; ShareAlike-licensed sources (the Wikimedia adjacency *graph*, the GeoDataSource country-borders CSV) are used only as test oracles, never shipped as assets; GPL/AGPL code (Domination, openfrontio) is read for ideas and never copied.

**Why.** `Risk_board.svg`'s own source metadata reads, verbatim, "Own work by uploader — based on a Risk board i own" — the uploader never held rights to Hasbro's board art, so the CC BY-SA tag cannot grant what was never theirs to license, and `Risk_game_board.svg` is a second-generation derivative of the same defect (`research/02-maps-and-fan-code.md` §B.5). This is flagged as the single biggest trap in the whole map-research lane, specifically because the starting assumption that a clean public-domain Risk SVG exists on Wikimedia Commons turns out to be false.

**Consequence.** Every map geometry decision in this log (D36, D37, D40) routes exclusively through Unlicense/Apache-2.0/public-domain/ISC sources (TotalRisk, Natural Earth, `world-atlas`, `BlankMap-World.svg`), never through the tempting-but-tainted Wikimedia board family.

## D39 — Middle Earth ships only under original names and only if geometry can be generated; tiny boards become engine fixtures

**Decision.** Middle Earth ships, if at all, only with original (non-Tolkien) place names, and only if geometry can be generated for its MIT-licensed 38-territory graph, which currently has none; otherwise it is skipped entirely. The Tiny3/Tiny4/Mini toy boards ship as engine unit-test fixtures and the end-to-end tiny map, not as player-facing content.

**Why.** Middle Earth's graph is cleanly MIT-licensed, but its place-names are Tolkien Estate intellectual property regardless of the graph's own licence, and it has no shipped geometry at all to draw it with — two independent blockers, either of which alone would be reason to defer it (`research/02-maps-and-fan-code.md` §A.3). The tiny fixture boards, by contrast, exist specifically because they are small enough to reason about exhaustively in a unit test, which is a different job from being a fun map to actually play on.

**Consequence.** Middle Earth is explicitly not part of the 13-map Tier 1–4 count in D37 unless a future geometry pass unblocks it under original names; the tiny boards never appear in the in-game map picker at all.

---

## D40 — Map data is lazy-loaded per map, and raw geodata sources never enter the client bundle

**Decision.** Each map's JSON is lazy-loaded only when that map is selected; the raw geodata sources used to *build* the regional maps (Natural Earth shapefiles, `world-atlas`/`us-atlas` TopoJSON, `BlankMap-World.svg`) live in `research/map-data/` and the build pipeline, and never ship inside the client bundle.

**Why.** Thirteen boards' worth of geometry in the initial bundle would dominate it, while each map's simplified, per-territory JSON (per D36) stays well under 100 KB on its own, which is only sensible if maps are fetched individually rather than all at once (`research/02-maps-and-fan-code.md` §B.6). The raw source data used to *generate* those maps is an order of magnitude larger again and has no runtime purpose whatsoever once a map's simplified JSON has been produced.

**Consequence.** Opening the map picker loads only each map's name/thumbnail metadata; selecting a map triggers exactly one additional fetch for that map's full JSON, and the build pipeline's own geodata dependencies never appear in `next build`'s output at all.

## D41 — Chat is preset-only — a 42-line roster plus a small code-drawn emoji set — shown as a timed speech bubble and logged **[mostly ours; five lines plus the ally-only pair are RGD-verbatim]**

**Decision.** Chat is preset-only, never free text: a roster of roughly 42 lines grouped by category (greetings, diplomacy, threats, reactions, apologies, encouragement, endgame), of which exactly five lines are kept verbatim from confirmed RGD evidence (`NO DICE`, its retired predecessor `THE DICE HATE ME!`, `Great game`, and the two ally-only lines `attack my territory if you need to` / `sorry, I need to attack your territory`), plus a small set of code-drawn emoji reactions of our own. A sent line appears as a speech bubble on the sender's roster capsule for roughly four seconds and is logged to the chat history.

**Why.** SMG's family-friendly licensing explicitly forbids free text in casual play — "an unsupervised minor chat with an adult stranger" is the developer's own stated reason — so the mechanism (preset lines only) is confirmed RGD parity, but almost the entire *content* of the roster beyond the five verified lines is our own proposal, written to match RGD's observed tone (short, punchy, exclamation-heavy, never hostile) rather than transcribed from the live game, since no source yielded a complete verbatim list (`research/03-ux-flow-modes-dialog.md` §5, §5.4). The emoji set is drawn from our own code rather than reproducing SMG's paid "Emotes Pack: The General" DLC art, both because we cannot license it and because the store art already establishes that a simple drawn glyph (a bot's `…` thinking bubble) fits the house style.

**Consequence.** Any future expansion of the chat roster is understood to be our own writing in RGD's voice, not a transcription — the five RGD-verbatim lines and the two ally-only lines are the only strings in the whole set that must never be edited for "improvement."

## D42 — Bots may fire a few reaction lines on events, an addition of our own beyond RGD's bot behaviour **[ours]**

**Decision.** Bots may fire a small number of reaction lines on specific events — losing a territory, a bad roll, being eliminated — explicitly flagged as our own addition rather than confirmed RGD behaviour.

**Why.** No source confirms RGD's bots emit any preset chat of their own, but the store art already shows a bot "…" thinking-bubble affordance (`crop-*`/`store/play-16.jpg` evidence underlying `research/04-visual-design.md` §6, item 18), which establishes that the visual language for "the bot is communicating something" already exists in the reference material and costs little to extend to a handful of reaction lines. It is cheap characterisation that gives bots the same small personality touch the persona system (D28) already gives their play style.

**Consequence.** These lines draw from the same preset chat system as human players (D41), not a separate bot-only vocabulary, and must stay clearly labelled in any future documentation as an addition, not a replication.

## D43 — Land is filled per the current owner's colour, not by continent, contradicting the classic board game

**Decision.** In play, every territory's top face is filled with its *current owner's* colour, not its continent's colour — continent identity is visible only on demand, via the Continent Overlay (which replaces owner fills with per-continent tints and draws a glowing stroke around each continent's outer perimeter), or as a perimeter glow drawn around any continent a player fully controls without the overlay active.

**Why.** This is flagged in the visual-design research as "the single most important finding, and it contradicts the classic board game" — direct pixel evidence shows North Africa, Egypt and Middle East rendered green (one owner) while China, India and Siam render red (a different owner) and Brazil/Peru/Argentina render purple, cutting directly across continent boundaries the physical Hasbro board always colours as fixed regions (`research/04-visual-design.md` §1.4; evidence `bt1-0200-deploy-troops-slider-territory-labels.jpg`, `nyc-0115-nyc-map-six-player-sidebar.jpg`). The menu/picker renders deliberately invert this treatment — parchment-cream land with continent-coloured *outlines* — confirmed as the one place the classic colour-by-continent convention survives (`wiki-classic-map.jpg`, `mappick-europe.jpg`).

**Consequence.** The renderer needs exactly one colour source — the owning player — for the live board, and a second, entirely separate palette (the continent accent set) only for the overlay and the picker tiles; off-board/unplayable land gets its own neutral grey rather than any owner or continent colour at all.

## D44 — The player roster is a vertical stack of capsules flush to the right edge, bleeding off-screen, not a top bar

**Decision.** The player roster renders as a vertical stack of capsules flush to the screen's right edge, each row bleeding off the right side of the frame rather than being fully contained within it; it is never a horizontal top bar.

**Why.** This is called out explicitly as "a defining layout choice" of RGD's HUD, confirmed across multiple independent frames and crops at consistent measured proportions (stack x-range 87.2–100% of frame width, row pitch ≈13.9% of frame height) — not a one-off composition accident (`research/04-visual-design.md` §4.4; evidence `crop-player-roster-sidebar.png`, `crop-player-roster-fogged.png`, `nyc-0115-nyc-map-six-player-sidebar.jpg`, `bt5-0108-territory-cards-seized-on-elimination.jpg`). The active player's capsule is additionally the one row that departs from the translucent-stroke style of the others — it fills solid with the owner colour and widens, with a small chevron tab poking past the edge — which is itself confirmed across frames, not inferred.

**Consequence.** On narrow viewports the roster rows shrink and drop their secondary line rather than relocating to a top bar; only the portrait-mode design (D49) actually moves the roster to a horizontal strip, and that move is explicitly our own invention for a constraint RGD itself never has to solve.

## D45 — Every piece of text drawn over the board carries a heavy dark outline and drop shadow — the outline is the font

**Decision.** Every piece of UI text that sits over the board — territory labels, token numerals, phase labels, dialog titles — carries a 3–4 px near-black stroke (`paint-order: stroke fill`) plus a 2 px drop shadow, regardless of which typeface ends up chosen.

**Why.** This is singled out as "the single most characteristic typographic move" in the whole visual-design research, confirmed by direct measurement across territory labels, the "Deploy Troops" dialog title, and every troop-count numeral in the evidence set, and the research states flatly that "without it the replica will not read as RGD whatever typeface is chosen" (`research/04-visual-design.md` §2.6, §5.5; evidence `bt1-0200-deploy-troops-slider-territory-labels.jpg`). This treatment is independent of and more load-bearing than the exact typeface decision (D73) — it is the thing doing the actual work of reading as "RGD," with the font choice secondary.

**Consequence.** The outline-and-shadow treatment is a single shared CSS class (`.on-board-text`) applied uniformly, so a future change to the typeface token never risks silently dropping the stroke that makes text legible over a busy, multi-coloured board.

## D46 — The camera is flat 2D SVG plus a single perspective rotateX transform, never a real 3D scene

**Decision.** The board is rendered as flat 2D SVG with a single CSS `transform: perspective(1400px) rotateX(θ)` applied to the map wrapper — θ = 4° at rest, animating to 18° (with a 2.2× scale) for the battle close-up — rather than any genuine 3D rendering.

**Why.** Measured side-wall heights at rest (only 6–10 px, visible solely along landmass bottom edges) versus at the zoomed battle view (18–24 px, with a visible lit bevel at the board's edge beyond which the frame goes pure black) are consistent with exactly this single-property camera model reproducing "the whole camera language" of the reference game without building any actual 3D geometry (`research/04-visual-design.md` §1.2; evidence `bt3-0052-continent-overlay-bonus-legend.jpg`, `bt5-0108-territory-cards-seized-on-elimination.jpg`, `bt2-0025-blitz-win-chance-100-attack-limit.jpg`). The much stronger, fixed ~30°-tilt-plus-6°-yaw camera seen on map-picker tiles is deliberately a separate, "product shot" camera used only in menus — it is not the in-play camera scaled up.

**Consequence.** Tokens and labels must live in an HTML layer outside the transformed SVG (D48), specifically because they must not inherit the `rotateX` skew the board itself gets — a number rendered inside the tilted SVG would read at an unreadable angle.

## D47 — The Blitz win-chance percentage is a constant gold colour at every probability, with an opt-in ramp flagged as our deviation **[opt-in ramp is ours]**

**Decision.** The Blitz Win Chance readout renders in a constant gold (`#F0C40F`) at every probability from 6% up to 100% — only the number changes, not the colour. An optional, opt-in colour ramp (green at ≥90%, amber-gold at 40–69%, red below 15%) is offered as a usability improvement, explicitly flagged as a deviation from the reference rather than claimed as parity.

**Why.** Direct pixel sampling of the percentage readout across five different odds frames (100%, 99%, 91%, 46%, 6%) all land within JPEG-noise distance of the same gold hue — the assumption of a probability-driven colour ramp is directly contradicted by the evidence, which states flatly "there is not one" (`research/04-visual-design.md` §2.7; evidence `bt2-0025-blitz-win-chance-100-attack-limit.jpg`, `bt2-0150-blitz-win-chance-6-low-odds.jpg`, `bt6-0050-blitz-win-chance-46-attack-limit.jpg`).

**Consequence.** The default build is faithful to RGD even where that looks like a missed usability opportunity; the ramp exists only behind a settings toggle, so a screenshot of the default experience always matches the reference exactly.

## D48 — Troop tokens and labels live in an HTML layer above the SVG map, with no collision avoidance between them

**Decision.** Troop-count tokens and territory-name labels are rendered in an HTML layer positioned absolutely above the SVG board, anchored at each territory's precomputed pole-of-inaccessibility point, with deliberately no collision-avoidance logic between overlapping labels.

**Why.** Keeping tokens and labels outside the SVG is what lets them avoid the board's own `rotateX` camera skew (D46) and use ordinary text rendering, `text-stroke`, and standard accessibility semantics rather than fighting SVG's text model. The "no collision avoidance" half of the decision is directly evidenced, not an oversight: a zoomed frame shows "Northwest Territory" and "Eastern United States" labels spilling well past their own borders and simply overlapping their neighbours' labels with no attempt at avoidance, and labels are hidden entirely below a roughly 2,500 px² on-screen-area threshold on dense maps rather than being algorithmically repositioned (`research/04-visual-design.md` §8.5, §8.6; evidence `bt5-0108-territory-cards-seized-on-elimination.jpg`, `nyc-0115-nyc-map-six-player-sidebar.jpg`).

**Consequence.** The label-placement code is deliberately simple — compute one anchor point per territory with `polylabel`, position the label a fixed offset below the token, and hide it under an area threshold — with no budget spent on a collision solver RGD itself never built either.

## D49 — The game is landscape-first with a from-scratch portrait layout, plus a per-player pattern-overlay accessibility toggle **[portrait layout is ours — no evidence exists for it]**

**Decision.** The primary experience is landscape, matching every one of the 304 reference images collected (including every store screenshot). A portrait layout is nonetheless designed from scratch — roster collapses to a horizontal top strip, modals become full-width sheets, the Blitz view stacks attacker-above-defender — since a browser cannot lock orientation the way a native app can. A per-player pattern-overlay toggle (dots, diagonal, cross-hatch at 12% white) is additionally offered for colour-vision accessibility.

**Why.** Every single piece of evidence gathered — store screenshots up to 2560×1600, every gameplay video frame — is landscape; there is no portrait frame anywhere in the evidence set, so the portrait design is stated plainly as "my design," not an inference from any reference material (`research/04-visual-design.md` §7.1, §7.2, §9). The pattern-overlay toggle responds to a real, identified risk in the confirmed player-colour palette: Red/Pink and Green/Yellow are specifically flagged as the pairs most likely to be confused under common colour-vision deficiency, and the game's own blizzard-tile hatching already establishes that a hatched-pattern treatment fits the established art style.

**Consequence.** Portrait mode is explicitly a browser-only accommodation that RGD's native apps never had to design, and should be understood by any future contributor as original UX work rather than something to "fix" toward a reference screenshot that does not exist.

## D52 — `getDb()` is memoised on `globalThis` via a Symbol, and PGlite is refused under production unless explicitly escaped

**Decision.** The database handle is memoised on `globalThis` via `Symbol.for("risk.db")` (not a module-level `let`), and PGlite is refused under `NODE_ENV=production` unless `E2E_ALLOW_PGLITE_PRODUCTION_BUILD=true` is explicitly set *and* no serverless marker (`VERCEL`, `AWS_LAMBDA_FUNCTION_NAME`, `NETLIFY`, etc.) is present in the environment.

**Why.** Next.js builds several separate module graphs per app (server components, route handlers, server actions), and a module-scoped singleton is therefore a singleton *per graph*, not per process — with PGlite specifically, that means several WASM Postgres instances opening against one data directory and corrupting its write-ahead log, which island-empire's own adapter documentation calls out by name (`research/00-repo-conventions.md` §2; `research/06-online-play-free-tier.md` §3.1). The production guard matters more for an online game than it did for island-empire's map-sharing use case: silently falling back to a per-instance PGlite online would mean every player is talking to a different, empty copy of the game, which is a correctness failure, not just a performance one.

**Consequence.** The escape hatch structurally cannot fire on a real Vercel deployment even if the environment variable somehow leaked there, because the serverless-marker check is independent of and in addition to the explicit opt-in flag.

## D53 — Playwright runs a single worker with no parallelism, and e2e drives the poll through a debug handle instead of sleeping

**Decision.** `playwright.config.ts` sets `workers: 1` and `fullyParallel: false`, and the e2e suite drives the client's poll directly through an injected debug handle (`window.__riskDebug.pollNow()`) rather than sleeping for a fixed interval and waiting for a real poll to happen naturally.

**Why.** Two Playwright workers means two `next start` processes means two PGlite instances against one data directory — the exact WAL-corruption scenario D52's guard exists to prevent — so the two "players" in a two-context test would literally be in different universes rather than sharing one game (`research/06-online-play-free-tier.md` §6.2). Sleeping the real poll interval (2.5 s) after every move, rather than driving it on demand, was separately measured to make the suite take roughly ten minutes; driving the poll directly is the super-smash-style lesson that "pixels can only tell you something was painted... not whether the simulation moved" applied to network timing rather than rendering (`research/06-online-play-free-tier.md` §6.3).

**Consequence.** Every e2e test that needs two players to see each other's moves calls `sync(pageA, pageB)` rather than `page.waitForTimeout(...)`, which makes the suite both correct (no WAL corruption) and fast (seconds, not minutes).

## D54 — The very first test written is the replay determinism proof: fold the log and match every stored hash

**Decision.** The first test written against the engine is the replay-determinism proof: fold the entire action log from `seq = 0` through `apply` and assert that the resulting `hashState` matches every stored `state_hash`, for a set of real and bot-vs-bot games.

**Why.** This test needs no second browser context, no network, and no server — it is pure data plus the pure engine — and every other guarantee this design makes (idempotent retries, desync detection, golden-hash regression tests) is only meaningful if `apply` is actually, verifiably deterministic to begin with (`research/06-online-play-free-tier.md` §6.4). Writing it first, before anything that depends on it, is the cheapest possible way to catch a determinism violation before it is buried under a stack of other code that assumes determinism already holds.

**Consequence.** Any future bug report that smells like a desync should be reproducible by feeding the reported game's action log into this exact test before looking anywhere else.

## D55 — Golden replay hashes for bot-vs-bot games are versioned artefacts, and a heuristic change that moves one is deliberate

**Decision.** A suite of golden replay hashes — `(seed, map, settings, persona assignment)` plus a hash of the state after every turn, for a few hundred full bot-vs-bot games — is stored as versioned test artefacts. Any heuristic change that moves one of these hashes is treated as an explicit, intentional, recorded change, never an incidental side effect; the ruleset itself is versioned so an old replay keeps playing back correctly against the bot code it was recorded with.

**Why.** Without this, any bot tuning change — adjusting a persona weight, fixing a minor heuristic bug — silently invalidates every previously stored replay the moment it shifts even one decision in one game, because the bot's decisions are themselves part of the deterministic sequence being replayed (`research/05-bots-and-ai.md` §7.2). Treating a hash move as a *decision* rather than an incident is what turns "oops, we broke old replays" into "we shipped ruleset v2, and v1 replays still play back against v1's frozen bot code."

**Consequence.** Bumping the ruleset version is the one and only sanctioned way to let a bot-heuristic change move a golden hash — a change that moves a golden hash without bumping the version number should fail review on sight.

## D56 — The forced-trade threshold is five or more cards at turn start, resolving a rulebook/RGD wording contradiction

**Decision.** Holding five or more cards at the start of a turn forces at least one set to be traded in (and a second, if you still hold a full set afterward) — "five or more," not "exactly five."

**Why.** The 2003 Hasbro rulebook states this unambiguously as "5 or 6 cards... must trade in at least one set," the highest-authority source available, while SMG's own support article was summarised by an automated fetch tool as "exactly 5 cards" — a paraphrase, not a verbatim quote, and one that could not be independently re-verified character-for-character (`research/01-core-rules.md` §3.6). The two readings are reconciled rather than left contradictory: since card count can never normally exceed 6 under the rules this very system enforces, "exactly 5" and "5 or more" produce identical observable behaviour in every reachable game state, so the rulebook's own unambiguous wording is adopted as the safer, better-sourced interpretation.

**Consequence.** This threshold is what D20's "three distinct card-timing branches" is numerically built on; a future discovery that RGD's live client genuinely enforces a stricter "exactly 5" rule in some edge case would be a correction to this entry specifically, not to D20's branch structure.

## D57 — Capitals grants only the win condition and the defender's third die by default; the +2 draft bonus ships off as a flag

**Decision.** The Capitals mode implements only the every-capital win condition and the capital's +1 defender die (making a capital assault 3-dice-vs-3-dice rather than 3-vs-2). The additional "+2 troops every Draft phase for holding your capital" rule is implemented as a real, working modifier flag, but it ships **off by default**.

**Why.** One lane of evidence states the +2 draft bonus as if it were simply part of Capitals, while the higher-authority rules research sources only the win condition and the defender's extra die, with no citation found for a +2 draft bonus anywhere in the primary rulebook or SMG's own support articles (`research/03-ux-flow-modes-dialog.md` §2.1 vs. `research/01-core-rules.md` §6.2). Rather than silently picking one source over the other, both are honoured: the unsourced claim becomes a real, documented, off-by-default modifier rather than either a hard-coded rule or a discarded idea, which keeps the door open if it is later confirmed against a live client.

**Consequence.** Turning the flag on changes nothing about the dice math (D27) — it is purely an extra reinforcement amount applied at draft time — so it can be toggled without touching the combat code at all.

## D58 — Unstable portals relocate on a fixed 3-round cadence and sit inactive for the round after each move

**Decision.** An Unstable portal relocates to a new destination on a fixed cadence of every 3 rounds, and sits inactive for the single round immediately following each relocation.

**Why.** Two sources disagree on the mechanism — one describes Unstable portals as "randomised destination each time" (implying a random *trigger*, not just a random destination), the other as relocating "every few turns, inactive for one turn after moving" (`research/02-maps-and-fan-code.md` §A.1 vs. `research/03-ux-flow-modes-dialog.md` §2.2). The second, more specific reading is adopted because it fully specifies both the *when* (a cadence) and the *consequence* (a cooldown), where the first reading only specifies the *destination* and says nothing about timing at all — the more complete description is both more useful to implement against and not actually contradicted by the vaguer one, since a fixed-cadence relocation can still land on a randomised destination.

**Consequence.** Both Unstable and Stable portals share one data model (a pair of linked territories), differing only in whether `relocateEveryNRounds` is set; a Stable portal is simply the degenerate case where it never relocates.

## D59 — Max Rounds ships off by default with a 5-round preset labelled 5-Rounds Rumble, tied by territories then troops

**Decision.** The Max Rounds modifier ships off by default, with a preset of exactly 5 rounds labelled **5-Rounds Rumble** in the UI; when the round limit is reached, the winner is whoever holds the most territories, with ties broken by total troop count.

**Why.** An official SMG/RISK Facebook post directly confirms the mode's existence and its marketing name — "5-Rounds-Rumble: Rush to victory in 5 turns!" — making the preset number and the label itself a primary-sourced fact, but no source anywhere states what actually happens at the round limit if the leader is ambiguous (`research/01-core-rules.md` §6.5; `research/03-ux-flow-modes-dialog.md` §2.1). "Most territories, then most troops" is adopted as the tiebreak because it is the simplest rule consistent with the mode's own stated purpose — rewarding aggression and expansion over slow accumulation — and requires no additional state beyond what every other win-condition check already reads.

**Consequence.** A game using the generic Max Rounds modifier at any preset other than 5 uses the identical tiebreak rule; "5-Rounds Rumble" is purely a labelled shortcut for `maxRounds: 5`, not a separately-coded mode.

## D60 — Percentage Domination defaults to 70% and is adjustable from 50% to 90%, since only 70% is directly sourced

**Decision.** Percentage Domination defaults to 70% of the current map's total territories and is adjustable anywhere from 50% to 90%.

**Why.** The only primary-sourced figure found anywhere is 70%, confirmed directly by an official SMG/RISK Facebook post naming the mode "Percentage Domination: Whoever rules 70% of the world, wins!" — no source gives the adjustable range's actual bounds (`research/01-core-rules.md` §6.5). A 50–90% window is chosen as a reasonable, symmetric-feeling range around the one confirmed number rather than inventing an unrelated range or, worse, shipping the mode as a fixed 70% with no adjustability at all, which would under-deliver relative to community descriptions of it as a tunable "game modifier."

**Consequence.** Any future discovery of RGD's actual adjustable bounds would correct only the two endpoint numbers in this entry; the 70% default itself is already primary-sourced and would not change.

## D61 — The turn timer ships the community-sourced 60/90/120/180/300-second list, online only, defaulting to 90 seconds

**Decision.** The turn timer, available only in online play, offers exactly the five durations 60s/90s/120s/180s/300s, defaulting to **90 seconds** rather than RGD's own apparent matchmaking default of 60 seconds.

**Why.** The five-value list itself is community-sourced, not confirmed by an official settings-list page, though its existence and general shape are well corroborated across multiple independent Steam discussion threads (`research/01-core-rules.md` §6.8). The 90-second default deliberately departs from RGD's own reported 60-second matchmaking norm — community discussion explicitly states "90% of available games use 60-second timers" for RGD's competitive ranked audience — because this replica's casual, no-stakes context suits a slightly less pressured pace better than copying a competitive-matchmaking default that exists to keep ranked games fast.

**Consequence.** This is a disclosed, deliberate deviation from RGD's own observed norm, not a parity claim — a future contributor should not "fix" the default back to 60s under the assumption that 90s was a mistake.

## D62 — A seat becomes a bot after two missed turns and two minutes unseen, and flips back on the player's next poll

**Decision.** Missing your turn deadline auto-ends the current phase or turn. After **2 missed turns** *and* your last heartbeat being older than **2 minutes**, your seat flips to a bot (`seat_to_bot`); the moment you poll again, it flips straight back to human (`seat_to_human`) with your missed-turn count reset.

**Why.** No official RGD source states an exact "after N missed turns" rule at all — the only hard numbers found anywhere are those worked out directly for this project's own online design, derived from first principles about what a casual, no-penalty replacement rule should feel like (`research/03-ux-flow-modes-dialog.md` §4.3; `research/06-online-play-free-tier.md` §4.5.4). Requiring *both* conditions, not just the timer and not just the heartbeat, avoids two failure modes individually: a player who is simply slow but still present should not be bot-replaced on a timer alone, and a player who went silent mid-turn-timer should not need to miss a second full cycle before the game moves on without them.

**Consequence.** Both conditions and the takeover/reconnect itself are rows in the action log (D14), so a replay faithfully reconstructs exactly when and why a seat was ever a bot, even though the *rule* producing that row is our own design rather than RGD's documented behaviour.

## D63 — Alliance loyalty is near-absolute at low bot tiers and only rarely, decisively broken at Expert

**Decision.** Bot `allianceLoyalty` is 1.0 (never betrays) at Beginner through Medium, 0.9 at Hard, and 0.6 at Expert — and when Expert *does* betray, it is written to be rare and decisive (typically only when betrayal wins the game outright, or against the runaway leader), never a repeated small nibble.

**Why.** There is no first-party RGD statement on bots and alliances at all; the only concrete datum found is a single unanswered 2020 player bug report that a bot replacing an ally "will not attack you, even if you attack them" (`research/05-bots-and-ai.md` §1.3). Treating low tiers as faithfully loyal matches that lone report and the folk belief it supports ("bots never break alliances"), while giving only Expert a real, if limited, capacity to betray is the deliberate design choice that keeps low tiers predictable and trustworthy while giving the hardest tier a genuinely higher ceiling — one a human expert player would actually have to watch for.

**Consequence.** Betrayal logic only needs to exist in Expert's decision path at all; lower tiers can treat an active alliance as a hard constraint with zero scoring overhead.

## D64 — A 2-player game uses the rulebook's 40/40/40 armies and 14/14/14 territory split, since RGD's own figures are unverified

**Decision.** A 2-player game uses the official rulebook's dedicated 2-player variant exactly: 40 armies per side (player, opponent, and a third "neutral" buffer colour) distributed as 14/14/14 territories across the map, with neutral armies never attacking and never receiving reinforcements.

**Why.** This is the print rulebook's own explicit, fully-specified dedicated 2-player appendix, and it is the only fully-sourced figure available — the RGD-specific fandom-wiki page describing its digital 2-player ("1v1") mode could not be fetched at any confidence this pass, so no RGD-specific override exists to adopt instead (`research/01-core-rules.md` §1.3).

**Consequence.** The neutral colour's territories and armies are modelled as a genuine, non-eliminable third "player" that never takes a turn, rather than as a simplified map obstacle, so the dice math and card-earning rules all still apply correctly when a human attacks a neutral-held territory.

## D65 — Auto Placement distributes armies evenly across each seat's assigned territories, with a seeded, policy-driven remainder

**Decision.** With Auto Placement on (the default), starting armies are distributed as evenly as possible across each seat's randomly-assigned territories, with any remainder placed according to the same `secure` border-reinforcement policy the AI uses elsewhere, and the whole process is seeded for determinism.

**Why.** No official SMG source gives any numeric formula for how Auto Placement distributes armies once territories are assigned — the only confirmed fact is that the territory *assignment* itself is random and roughly fair (`research/01-core-rules.md` §1.5). Reusing the already-specified `secure`/BSR-weighted placement policy (`research/05-bots-and-ai.md` §3.1) for the leftover-army distribution, rather than inventing a second, unrelated distribution rule, means the starting board is never *worse* defended than a mediocre human player would leave it, and it costs no new code.

**Consequence.** Auto Placement and a bot's own in-game reinforcement logic share one placement function; changing one tunes both.

## D66 — The jump-to-max post-conquest control is labelled Move All, a naming choice of ours with no SMG citation **[ours]**

**Decision.** The jump-to-max shortcut on the post-conquest troop-movement slider is labelled **Move All**.

## D67 — The Blitz Attack Limiter is implemented as SMG's `stopUntil` truncation, without claiming the stop rule is optimal

**Decision.** The Blitz Attack Limiter is implemented as SMG's own `stopUntil` mechanism — a slider that truncates the outcome distribution at a chosen troop-commitment point, introducing a third `UnresolvedChance` outcome alongside clean win/loss — and the implementation explicitly does not claim this stop rule is strategically optimal.

**Why.** The limiter's existence and its slider-based UI are confirmed with medium confidence from community/patch-note sourcing, and SMG's own shipped `risk-dice` code is confirmed to model it exactly this way (`research/01-core-rules.md` §4.2; `research/05-bots-and-ai.md` §2.13). The explicit non-claim of optimality matters because every published battle-odds table in the literature — including the one this project's own DP computes (D22) — assumes fight-to-the-death; a player's option to stop mid-battle via the limiter is a free option whose value none of the surveyed academic papers actually solved, Tan (1997) having flagged it as an open problem decades ago.

**Consequence.** The Attack Limit slider and its `UnresolvedChance` outcome are modelled as a genuinely separate code path from the plain win/loss battle resolver, and no part of the UI implies the chosen stop point was mathematically the best one to pick.

## D70 — A troop token above two digits widens into a stadium shape and truncates past three digits, never shrinks past legibility

**Decision.** A troop-count token holding one or two digits stays a fixed-size circular disc with the numeral condensed as needed; past two digits, the disc widens into a stadium/pill shape (`rx = r`, width growing with digit count) rather than shrinking the type further, and the display is capped at three digits with `99+`-style truncation beyond that.

**Why.** No frame in the entire evidence set shows a troop count above 14, so the three-digit treatment has no direct observation to extrapolate from at all; the decision instead reasons from two separate, independent pieces of evidence — the confirmed two-digit behaviour (disc size fixed, numeral condensed to roughly 0.52× its one-digit scale) and the older store-art generation, which already shows stadium-shaped tokens as an established, in-family shape (`research/04-visual-design.md` §3.2, §9; evidence `store/play-16.jpg`).

**Consequence.** The token component needs a width that is a function of digit count above two digits, not a fixed-size circle with ever-shrinking text — the opposite of the two-digit case's own treatment, and the two rules must not be confused when implementing the component.

## D72 — Every motion duration and easing curve is our own invention calibrated to the art, and prefers-reduced-motion is honoured **[ours]**

**Decision.** Every animation duration, easing curve, and timing value in the motion specification (turn-start banners, dice tumbles, capture wipes, card deals, and the rest of the 25-entry motion table) is our own invented recommendation, chosen to match the visual weight of the confirmed art direction rather than measured from any video evidence; `prefers-reduced-motion` is honoured throughout, with the heaviest animations (dice tumble, victory stars, ocean-line drift) dropped entirely and others (phase transitions, token-count ticks, capture wipes) collapsed to instant state changes.

**Why.** Every single piece of visual evidence gathered for this project is a still frame — no video was examined frame-by-frame for motion timing — so while a still-frame diff can *confirm an animation exists* (two frames differ in a way only motion could produce), it can never *confirm how that motion moves*, which the research states explicitly as its first and most consequential limitation (`research/04-visual-design.md` §6, §9). Specifying accessible fallbacks for each entry up front, rather than treating `prefers-reduced-motion` as an afterthought, costs nothing at design time and avoids a whole category of later retrofitting.

**Consequence.** None of the 25 motion-table entries should be treated as confirmed RGD behaviour in any future audit — only their *existence* (that something animates at that moment) is evidenced; their exact feel is design work.

## D73 — The headline typeface is Titillium Web paired with Barlow for body text, chosen by visual match, not identification

**Decision.** The headline/UI typeface is **Titillium Web** at weights 700/900, paired with **Barlow** for body text and captions, with numerals set `tabular-nums` so digits occupy identical widths on tokens and dice.

**Why.** The actual RGD typeface could not be identified from any source — the choice comes from enlarging three different pieces of in-game text 3–4× and matching their letterforms (a tall x-height, an open single-storey `g` with an unclosed descender hook, flat horizontally-cut terminals, mild condensation) against available Google Fonts, with Titillium Web judged the closest free match and Barlow Semi Condensed flagged as the fallback to A/B against if Titillium ever reads too technical (`research/04-visual-design.md` §5.5, §9). This decision is explicitly secondary to D45's outline-and-shadow treatment, which the same research states is what actually makes text read as RGD regardless of which font sits underneath it.

**Consequence.** A future contributor who identifies RGD's real typeface should treat this entry, not D45, as the one to revise — the outline treatment stays fixed either way.

## D74 — Every screen follows the current, darker bt* art generation, not the older lighter store screenshots it's cross-checked against

**Decision.** Every visual decision in this specification follows the current, darker, more-extruded `bt*` video-frame art generation (right-edge roster, deep ocean vignette, 3D-figurine battle view) rather than the flatter, lighter-blue, pill-token, bottom-centre-roster style visible in the older store screenshots. The older store shots are used only where they are the *sole* available evidence for a specific detail — chat bubbles, the bot "thinking" indicator, the turn-timer bar, and the high-resolution skull-disc elimination treatment — and each such use is individually flagged in its own entry (D42, D69, D70).

**Why.** The evidence set plainly mixes two distinct art generations: 2021-era store screenshots and current official SMG "Basic Training" video frames, and treating them as interchangeable would blend two different visual languages into one incoherent spec (`research/04-visual-design.md` §9). Explicitly committing to the current generation as the baseline, with named exceptions, is what lets every other visual decision in this log (D43–D49, D69–D71) cite a single consistent source of truth rather than silently averaging between two different-looking games.

**Consequence.** Any visual detail sourced from a `store/*.jpg` file anywhere else in this log should be understood as one of these deliberately-flagged exceptions, not as a quiet reversion to the older art style.

## D75 — Zombies mode ships out of v1, but its dice-augment plumbing stays in the dice model so it is cheap to add later

**Decision.** Zombies mode itself is out of v1 (per D34), but its two dice-math effects — an `attackDicePenalty` for a zombie attacker and a ties-favour-the-attacker rule for a zombie defender — are kept as live, working variants inside the shared dice-augment model (D27), even though nothing in v1 currently activates them.

**Why.** Every specific Zombies *gameplay* number (outbreak percentage, troop-conversion percentage) is genuinely unverified and was explicitly excluded from v1 for that reason, but the two dice-math effects are independently and separately confirmed — SMG's own `risk-dice` source lists Zombies as a supported dice augment exactly like Capitals, and SMG's own dice-odds FAQ explicitly names both the ties-to-attacker rule and the attacker's die penalty as augments that "STACK" with everything else (`research/01-core-rules.md` §6.6; `research/05-bots-and-ai.md` §4.6). Since D27 already builds the augment model as a small, enumerable set of integer bonuses/penalties rather than named modes, leaving the two confirmed Zombies entries wired into that same table costs nothing extra today and removes the one piece of Zombies that would otherwise need real engineering work later.

**Consequence.** Turning Zombies on in some future release is purely a matter of adding the unverified gameplay numbers (outbreak logic, conversion rate) on top of dice math that is already correct and already tested, rather than a combat-math project in its own right.

## D76 — Resigning turns the seat into a bot, through the same transition as an away takeover

**Decision.** `RESIGN` is not a separate elimination path. Online, the server appends `SEAT_TO_BOT` with `reason: "resigned"`; the seat keeps its territories and cards, a bot plays it from then on, and it cannot be reclaimed. Offline (Solo), resigning ends the human's session: they may watch the bots finish or leave. **[ours]** — RGD's own resignation semantics were not sourced.

**Why.** `research/06-online-play-free-tier.md §4.5.4` already defines one mechanism for a seat changing hands (timeout → bot → reclaim), and every such change is a row in the action log (D14). Neutralising a resigner's territories (`owner: null`) was considered and rejected: it hands a free continent to whichever neighbour is closest, so resigning becomes a weapon against a specific opponent. Gifting to a bot keeps the board's balance and reuses one code path.

**Consequence.** The engine needs no `RESIGN` reducer branch beyond `SEAT_TO_BOT`; the lobby/game UI shows the seat as "resigned" (skull-less, robot chip) and the `standing` column records `resigned`.
